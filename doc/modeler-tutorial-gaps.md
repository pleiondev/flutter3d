# Modeler tutorial — gaps journal

`tut-00`'s own "Журнал гэпов": every gap found while writing or walking
through a tutorial case, as one row. Accepted when this file is empty, or
every row below has become a `tut-NN` line in `doc/model-editor-plan.md`
with a decision — "делаем" or "откладываем" — recorded there.

| case | step | expected | actual | type | plan row |

| 1 | import (screen 21) | an agent driving the modeler over MCP can bring in an STL with a chosen unit and up axis, the way the app's own import screen (`import_plan.dart`, `screen/files.dart`) lets a person choose "mm" and weld/fix-normals/triangulate | `ModelSession.import`/the `import` MCP tool take only a path — no `ImportOptions`, no weld/fix-normals/triangulate flags. `import_into.dart` and `fromModelDocument` both take an `ImportOptions`; nothing above the session layer exposes it. Case 1's own fixture (`packages/flutter3d_model_mcp/test/fixtures/tutorial/case1_scenario.dart`) works around this by calling `fromModelDocument`/`importMeshData` directly rather than through `session.import`, which also means the import step is not on the case's own journal (see below) | function, agent-facing | tut-01 |
| 1 | diagnosis (mesh readiness) | `readiness.dart`'s `MeshChecks` (degenerate faces, non-manifold vertices, inverted shells) diagnose every geometry an object can hold | `_issuesWith`'s own `switch` only calls `MeshChecks` for `EditedGeometry`; an `ImportedGeometry` object — what any import is until something converts it — gets only `_morphTargetIssues`, so a freshly imported file with a genuinely broken mesh reads "ready to export" until the weld checkbox (or a mesh command) has turned it into an `EditedGeometry`. Real for case 1: `teapot.stl`, unwelded, shows zero issues; welded, it shows the one non-manifold vertex `MeshChecks` actually finds | integrity | tut-01 |
| — | `session.cleanup()`/`ModelHistory`'s journal marker | a recipe that finds nothing to do costs nothing on the undo stack (`ModelHistory.endTransaction`'s own doc comment: "a transaction in which nothing succeeded leaves no step") | true for `history`, not for `_journal`: `CommandJournal.beginTransaction`/`endTransaction` write their `{"transaction":"begin"}`/`{"transaction":"end"}` markers unconditionally, so a no-op `cleanup()` still writes two inert lines to the recovery journal (harmless on replay — an empty transaction is a no-op there too — but a person reading the raw `.jsonl` sees a pointless pair). Visible on `case1.jsonl` | UX (minor) | tut-01 |
| 1 | headless "expected result" render | `renderProject`'s own `_frame` fits the camera to whatever is in the project, at any scale, the way `OrbitController.frame` (the interactive viewport's own fit, floor `1e-4`) does | `render_project.dart`'s `_frame` floors its fitted bounding radius at `0.05` (5 cm). Case 1's own teapot, correctly imported at millimetre scale, is about 8 mm across — six times under that floor — so an unscaled render frames a handful of pixels in the middle of a 512×512 image instead of filling it. Confirmed by rendering `case1ImportedProject()` before adding a render-only 20× scale-up workaround (`tool/make_case1_fixtures.dart`'s own `_scaledForRender`, never applied to the exported fixtures). A person driving the real GUI does not hit this — only the headless render/renderSheet tools, which is exactly what the tutorial's own screenshots and case 6's agent-facing renders both depend on | function, tool-specific | tut-02 |

| 2 | operation card on a mesh edit (`ModelHistory.amend`) | an agent or a person adjusting the last edit through `ModelSession`/MCP the way the app's own operation card does | `ModelSession` has no `amend` method at all — the app calls `_history.amend(to)` directly on its own `ModelHistory` (`apps/flutter3d_modeler/lib/src/screen/interactions.dart`), bypassing `ModelSession`/`CommandJournal` entirely. `amend` works (verified in `tutorial_scenarios_test.dart`'s own case-2 group: it re-runs a mesh edit against the document before it, not on top of it), but nothing records the adjustment: a session's own `journal()` file still names the *original* argument on that step after an amend, not the last one actually applied | agent-facing, integrity | tut-03 |
| 2 | mesh editing (extrude/loop cut/bevel) | the three mesh-edit tools the plan names for this case | `flutter3d_mesh` has real `bevelEdges`/`bevelVertices` functions (`bevel.dart`), but no `ModelCommand` wraps either one — `apps/flutter3d_modeler/lib/src/ui/tools.dart`'s own comment already says "Inset, bevel and merge are" not tools. Case 2 exercises extrude and loop cut only; there is no command a case could call for a bevel | function | tut-04 |
| 2 | mesh editing (extrude/loop cut), modal transform | a case's own `.jsonl`, replayed through `CommandJournal.replay` from a cold `ModelProject`, rebuilds the document — the same promise case 1's journal keeps | `Extrude`/`LoopCut`/`TransformElements` all act on "whatever is currently selected", and selecting mesh elements is `ModelSession.select`, not a `ModelCommand` — its own doc comment already says object-level picking is "not something `CommandJournal` can replay". Case 2 is the first case whose edits actually depend on that at *mesh*-element level: its own journal, replayed cold, refuses at the first `extrude` with "no faces are selected to extrude" (`tutorial_scenarios_test.dart`'s own case-2 group asserts this exactly). A live session (a person clicking through the app, or an agent calling `select` then `run` over MCP) reaches the case's own fixture without trouble — only a *crash recovery* replaying the file alone cannot | integrity, agent-facing | tut-05 |
| 2 | modifier stack (mirror/array) | adding a modifier and seeing its effect — the viewport, a headless render, or an export all show what the stack currently produces | nothing reads `ModelObject.modifiers` except the properties panel's own list (`apps/flutter3d_modeler/lib/src/ui/properties/properties_panel.dart`) and `ApplyModifier`, which bakes the stack into the base mesh and then removes it. `SceneSync._dataOf` (the live viewport) reads `object.geometry` directly; `render_project.dart`/`render_sheet.dart` never mention `modifiers` either. A mirror or an array modifier is invisible everywhere until "Apply" is pressed — case 2's own page renders what the two modifiers actually produce by evaluating the stack by hand (`tool/make_case2_fixtures.dart`'s own `_withModifiersBaked`), the same three lines `ApplyModifier.apply` runs, because nothing else in this build can produce that picture | function | tut-06 |
