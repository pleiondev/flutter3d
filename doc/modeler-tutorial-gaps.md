every row below has become a `tut-NN` line in `doc/model-editor-plan.md`
with a decision — "делаем" or "откладываем" — recorded there.

| 2 | mesh editing (extrude/loop cut/bevel) | the three mesh-edit tools the plan names for this case | `flutter3d_mesh` has real `bevelEdges`/`bevelVertices` functions (`bevel.dart`), but no `ModelCommand` wraps either one — `apps/flutter3d_modeler/lib/src/ui/tools.dart`'s own comment already says "Inset, bevel and merge are" not tools. | 2 | mesh editing (extrude/loop cut), modal transform | a case's own `.jsonl`, replayed through `CommandJournal.replay` from a cold `ModelProject`, rebuilds the document — the same promise case 1's journal keeps | `Extrude`/`LoopCut`/`TransformElements` all act on "whatever is currently selected", and selecting mesh elements is `ModelSession.select`, not a `ModelCommand` — its own doc comment already says object-level picking is "not something `CommandJournal` can replay". Case 2 is the first case whose edits actually depend on that at *mesh*-element level: its own journal, replayed cold, refuses at the first `extrude` with "no faces are selected to extrude" (`tutorial_scenarios_test.dart`'s own case-2 group asserts this exactly). A live session (a person clicking through the app, or an agent calling `select` then `run` over MCP) reaches the case's own fixture without trouble — only a *crash recovery* replaying the file alone cannot | integrity, agent-facing | tut-05 |
| 2 | modifier stack (mirror/array) | adding a modifier and seeing its effect — the viewport, a headless render, or an export all show what the stack currently produces | nothing reads `ModelObject.modifiers` except the properties panel's own list (`apps/flutter3d_modeler/lib/src/ui/properties/properties_panel.dart`) and `ApplyModifier`, which bakes the stack into the base mesh and then removes it. `SceneSync._dataOf` (the live viewport) reads `object.geometry` directly; `render_project.dart`/`render_sheet.dart` never mention `modifiers` either. A mirror or an array modifier is invisible everywhere until "Apply" is pressed — case 2's own page renders what the two modifiers actually produce by evaluating the stack by hand (`tool/make_case2_fixtures.dart`'s own `_withModifiersBaked`), the same three lines `ApplyModifier.apply` runs, because nothing else in this build can produce that picture | function | tut-06 |
| 3 | Scene mode (light/shadow/environment/post), headless "expected result" render | `renderProject`/`renderSheet` — the same functions this tutorial's own reference pictures come from — draw a project's real `AddLight`/`SetLightField`/`SetEnvironment`/`SetSceneLightingField` settings, the way case 3's own point light, shadow request, studio environment and bloom should show up in its "what you get" picture | `render_project.dart`'s own `renderProject` builds a `Scene` with two fixed, hardcoded directional lights ("key"/"fill") and never reads `ModelProject.lighting` at all — not `lights`, not `environment`, not `ambientIntensity`/`shadows`/`exposure`/`post`. `render_sheet.dart`'s `renderSheet` calls `renderProject` for each quadrant, so it inherits the same blind spot. This confirms, at the headless-render layer, the exact gap `flutter3d_render_job`'s own `scene_from_project.dart` already names at the live-viewport-snapshot layer ("nothing in the application calls `LightingSync`" — `mat-23`'s still-unfinished wiring); checked directly, `grep -rn "LightingSync(" apps/flutter3d_modeler/lib/` finds one call site, inside `lightOverflowOf`'s own throwaway, never-drawn `Scene`. A project's own `SceneLighting` table is real and can be set, but nothing that draws a picture of the project — live main viewport, game-preview route, or either headless render tool — currently reads it except `LightGizmos` drawing the light's own marker. Case 3's own page renders the real geometry and placement of its two objects, but cannot show what its own lighting step actually does | function, tool-wide | tut-07 |
| 3 | import a second asset into an open project, from the app's own UI | a person clicking through the real GUI can merge a second file into a project already open — `mat-24`'s own extended scope (2026-09-09 decision) named this "Import into scene" via `ImportInto` | checked directly: nothing in `apps/flutter3d_modeler` calls `ModelSession.import` or the free `importInto` function at all. The toolbar's only file action is **Open** (`_openBytesWithImportScreen`'s own `openDocument`), which always replaces the whole document — the same path case 1's own import uses, never a merge. `mat-24` is recorded closed via `mat-34d` (2026-09-14), but `mat-34d`'s own text only wires the four Scene-mode panels (`SceneSourcePanel`/`SceneShadowsPanel`/`SceneEnvironmentPanel`/`ScenePostPanel`); it says nothing about an import action, and none exists. `ImportInto` itself is real and tested at the command layer (`import_into_test.dart`, `scene_multi_asset_export_test.dart`), and an agent over MCP already reaches it through `ModelSession.import` — only a person in the real app cannot. Case 3's own scenario drives it directly against the session, the same route an agent already has | function, app-facing | tut-08 |
| 4 | bending a joint (weights sub-mode's bend slider) | an agent over MCP, or a headless case, can reach the same pose a person's live bend slider previews | `ui/bend_slider_bar.dart`'s own doc comment is explicit: a bend turns the joint's live `SceneNode` directly and "never touches `ModelHistory`" — there is no `ModelCommand` behind it at all, by design (sixty frames of a drag are meant to cost nothing on the undo stack). The document-level equivalent an agent or a headless case actually has is `select` + `RotateBy` on the joint's own persisted `ModelObject.transform`, then `PoseJoint` to key it — case 4's own scenario uses exactly this, reaching the identical document state a person's slider drag would once *keyed*, through a different door than the live preview | agent-facing, by design | tut-09 |
| 4 | headless "expected result" render of a rigged, posed, morphed character | `renderProject`/`renderSheet` draw a project's real skin deformation and shape-key blend, the way case 4's own bent elbow and puffed chest should show up in its "what you get" picture | `render_project.dart` never mentions "skin" or "skeleton" anywhere in it (confirmed by grep while writing this case) — every mesh draws at its raw bind-pose position regardless of `ModelObject.skeletonIndex` or any joint's own transform — and it never mentions `shapeSet` either, so a shape key's own weight has no effect on the picture. Case 4's own reference render is real geometry, real materials, the file's own import, but shows neither the pose `PoseJoint` keyed nor the morph `AddShapeDriver`/`KeyShape` set up | function, tool-wide | tut-10 |
| 4 | headless render of the weight-paint gradient shading mode | `render`'s own `mode` argument (or some fourth one) draws the same weight-gradient visualization S4 built for the live viewport, so a case can show what a brush stroke actually painted without a window | `RenderShading` (`render_project.dart`) has exactly two members, `material` and `normals` — confirmed by reading the class directly — so neither `render` nor `renderSheet` can select anything like it at any layer. The real gradient shading (`weight_gradient.dart`'s five colour stops, an unlit material reading vertex colour) is a windowed-engine concept (`SurfaceShading`, `display_modes.dart`) `flutter3d_model_core` has no dependency path to reach, the same boundary `ShapeDriver`'s own doc comment already draws for "аддитивно через `MorphSink`" | function, tool-wide | tut-11 |
