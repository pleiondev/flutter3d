# Readiness review before 1.0.0-rc.1 (2026-10-09)

A read-only review of the working tree on branch `0.9.0`, run on 2026-10-09
after the waves of `1.0-scope-additions.md`, `1.0-arch-review.md`,
`1.0-boundaries.md` and `1.0-physics-audit.md`. Nine audits ran in parallel:
plans against the tree, the public documents, the public API, physical
constants, package boundaries, the renderer, the simulation and formats,
tests and publishing, and the engine-specific concerns the others do not
cover (hot path, precision, memory, threads, security). Each finding below
names its file and line as it was on that day.

Decisions taken on the same day, which shape the target state and the work
list:

- **The report lives here**, beside the other 1.0 plans.
- **rc.1 is blocked by the API shape too**, not only by what is wrong at
  run time or stops `pub publish`. A record or a `sealed` class that a user
  switches over is a major later, and rc.1 is the last free break.
- **Step D of the materials catalog goes into rc.1 in full**: the ~200
  substances with sources, the inelastic property group, and the
  `physicalMaterials` section of `.f3d`.

## 1. Verdict

**Not ready to tag.** The mechanical gates are green: `flutter analyze` is
clean, all 70 structure rules hold, every published pubspec is at
`1.0.0-rc.1` with `^1.0.0-rc.1` carets, every CHANGELOG's top heading is
right, the API, MCP, VM and CLI snapshots match the tree, and
`dart pub publish --dry-run` reports no error on any of the 56 publishable
packages. What is not green is everything the gates do not measure:

| Area | State |
|---|---|
| Fast test suites (19 plain-Dart packages) | 7 green, 12 red, **136 failures** |
| Goldens (Impeller, CPU, WebGL2, WebGPU) | all four older than the shaders of 2026-10-09; WebGPU not re-recorded at all |
| Tapes (`ascent.f3drun`, site platformer, racing) | older than the character controller of 2026-10-09; parity tests diverge at steps 5, 25, 75 |
| Silently wrong at run time | 5 findings (shooter rollback, prefab libm, origin shift on restore, genre snapshot of nothing, codec version skip) |
| Security | 3 findings (cloud convert reads host files, native snapshot trusts indices, MCP file tools without a root) |
| API shape | 10 "must" items that need a major after 1.0.0 |
| Physics homes | catalog and C header agree; cloth, sound and occlusion do not read the world; catalog data is 33 of ~200 |
| Git | 158 unpushed commits, ~3 400 uncommitted files, `packages/flutter3d_foundation/` **entirely untracked**, a history force-push pending |

The plans are closer to done than their own status notes say
(`1.0-boundaries.md` "cut off mid-work" is stale: B1, B3 and C are in the
tree), and further from done than the "Code done" marks suggest, because
"tests not run yet" turned out to mean 136 red tests.

## 2. What was found

Severity: **S1** wrong or unsafe for a user, silently; **S2** a break later
or a visible defect; **S3** should; **S4** nit. Confidence: *read*, *run*,
*suspected*.

### 2.1 Silently wrong at run time

1. **S1, read.** `FiredBy` is excluded from the shooter's snapshot
   (`flutter3d_game_shooter/lib/src/combat/projectile.dart:49`) and has no
   `InPlaceCodec`, so `EcsWorld.restore` (`flutter3d_sim/lib/src/ecs/ecs_world.dart:351`)
   clears it. After a rollback or `rewindTo` a rocket no longer ignores its
   shooter (`:155`) and credits nobody (`:175`); the resimulation digest
   differs from the original.
2. **S1, read.** Prefab expansion rotates entity positions through
   `Matrix3.rotationY` (`flutter3d_sim/lib/src/level/prefab.dart:413`),
   which calls libm `sin`/`cos`, not `Portable.sinCos`. A level with a
   yawed prefab instance differs in the last bit between the VM and the
   browser from step 0; `SimulationVersion` matches, so the refusal is not
   honest. The rule `a step asks no machine for an answer` greps for
   `math.sin` and misses this. Same hole: `Quaternion.axisAngle` in
   `flutter3d_physics_native/lib/src/native_ragdoll.dart:314`.
3. **S1, read.** `EngineLoop.restore` (`flutter3d_sim/lib/src/loop/engine_loop.dart:401-404, 834-839`)
   reads the origin back but calls no origin hook and publishes no
   `OriginShifted`. A rewind across a shift leaves the scene, the particles
   and the audio in the old frame. Nobody calls `shiftsPhysics`,
   `Scene.rebaseAround`, `EngineLoop.shiftOrigin` or `followOrigin` outside
   tests; the genres convert `body.position.toWorldPosition()` with the
   default origin (`flutter3d_game_platformer/lib/src/staging.dart:258`,
   `flutter3d_game_racing/lib/src/headless.dart:167`,
   `flutter3d_game_strategy/lib/src/headless.dart:238`,
   `flutter3d_sim_mcp/lib/src/sim_session.dart:569`). A `ParticleSystem`
   subscribed both through `Flutter3dEngine._shiftOrigin` and the
   declarative `Particles` moves twice (*suspected*). Latent until a game
   moves its origin, which none does today.
4. **S1, read.** `_GenrePart.capture()` returns `null` when the genre has
   no simulation (`flutter3d_sim/lib/src/loop/genre_plugin.dart:295-308`),
   `restore` swallows it and `Snapshots.restore` counts it as restored;
   `holdsNothing` (`ecs/snapshots.dart:54`) only counts `WorldSnapshotPart`.
   An empty world with a level-less genre passes `DeterminismCheck`
   trivially.
5. **S2, read.** A component whose saved codec version is newer than the
   running one is skipped (`ecs_world.dart:368, 396, 408`), so a 1.1 save
   opens in 1.0 without its entities and re-saves without them. Decisions 8
   and 9 of `1.0-stability.md` want a refusal with a reason.
6. **S2, read.** `EcsWorld.restore` drops `changedAt` and `save` never
   writes it (`ecs_world.dart:296-371`): a system on
   `query().changed<T>(since:)` behaves differently on the live step and on
   the resimulated one. No caller in `lib/` yet; the API is public.
7. **S2, read.** `Demo.checkSimulation` only runs when the caller passes a
   version (`flutter3d_game/lib/src/run/demo_timeline.dart:45`,
   `demo_recording.dart:254`). A 1.1 tape opens in 1.0 through the timeline
   and diverges at a checkpoint instead of refusing. `ghostOfRun` does it
   right.
8. **S2, suspected.** `RagdollCorpses` keeps its own native core with no
   `SnapshotPart` (`flutter3d_game_physics/lib/src/ragdoll/ragdoll_corpses.dart:44`);
   `BurningWrecks._burning` holds body handles that a `restoreElements`
   makes dangling (`wrecks/burning_wrecks.dart:38, 111`).
9. **S2, read.** `LocalSimulation.submit` during playback keeps `_pending`
   until the tape ends, then fires it all on the first live step and onto
   the recording (`flutter3d_sim/lib/src/loop/local_simulation.dart:77, 144`).
10. **S2, read.** `Flutter3dView` with a `frameRateCap` stalls after the
    ticker restarts: `Ticker.elapsed` starts from zero, `FrameCadence._lastDrawn`
    keeps the old value and nobody calls `reset()`
    (`flutter3d_app/lib/src/view/flutter3d_view.dart:618-640, 691-695`,
    `flutter3d_sim/lib/src/loop/frame_cadence.dart:66-86`). Pause for ten
    minutes with `frameRateCap: 30` and the view draws nothing for ten
    minutes, then steps the whole debt in one frame.
11. **S2, read.** `FrameCadence.cap` is a public mutable field; `_tick`
    writes `widget.frameRateCap` unchecked; `0` divides by zero
    (`frame_cadence.dart:46-52`). `Display.refreshRate == 0` is taken as a
    known rate and disables the cap (*suspected*, `flutter3d_view.dart:639`).
12. **S2, read.** `viewAxisOf` divides by `w = 0` for
    `PerspectiveProjection.infinite` (`flutter3d_core/lib/src/engine/scene/projection.dart:781-793`).
    Internal callers substitute a finite far; a plugin that hands
    `frame.viewProjection` to `Renderer.encodeScene` as `pass_contributor.dart:311`
    advises gets `ViewDepth = NaN` in the surface buffer.
13. **S3, read.** The fitted near plane (`renderer_depth.dart:455-464`)
    falls back to the authored near as soon as any contributor returns
    `null` from `boundsFor` (no override exists anywhere) or any node is
    not frustum-culled (sky domes). Plan item 5's "0.18 m shadow floor"
    gain therefore shows only in bare test scenes. The fit is keyed on
    `settings.reversedDepth`, not on the device's `reversed`, so WebGL
    without `EXT_clip_control` and Impeller on GLES carry the risk
    (stale `worldBounds` clipped) with no gain.
14. **S3, read.** Hashed alpha and cross-fade anchor their noise on
    `v_world_position`, which is scene space: every origin rebase re-rolls
    the pattern of all foliage for one frame; `fract(sin(x)·43758)` at
    `x ~ 1e5` is not bit-identical across GPUs (`surface.glsl:317`,
    `depth_predraw.frag:68`).
15. **S3, read.** `executeBundles` replays a plugin's bundle recorded with
    `less` into a reversed scene pass unturned
    (`renderer_depth.dart:178-183`); `ContributorFrame.reversedDepth`'s
    "nothing to do" is wrong for bundles.
16. **S3, read.** Two tests are red on tolerance, not code:
    `flutter3d/test/depth_precision_test.dart:98-108` (Float32 `Matrix4`,
    needs ~1e-6) and `lod_test.dart:447` (sRGB round-trip, needs `closeTo`).

### 2.2 Security and robustness

1. **S1, read.** The cloud's `convertFiles` checks `..` only on uploaded
   keys (`flutter3d_build/lib/src/convert/in_memory.dart:122`), not on
   references inside documents: `fileUriResolverFor`
   (`convert.dart:764-772`) opens `File('$directory/$uri')` unchecked,
   `usd_input.dart:81, 89` accepts absolute paths. A glTF with
   `"uri": "../../../../etc/passwd"`, an OBJ `mtllib ../..` or a USDA
   `@/Users/x/.ssh/id_rsa@` puts those bytes into the returned `.f3d`.
2. **S1, read.** The native snapshot's `consistent()`
   (`flutter3d_physics_native/csrc/src/f3d_snapshot.c:1139-1174`) does not
   check `F3dCompoundPart.hull` (dereferenced at `f3d_compound.c:246`,
   `hull == 0` reads `hulls[-1]`), mesh triangle indices against
   `vertex_count` (`:959`), `F3dShallowSlot.first + nx·nz·K` against
   `shallow_reals`, `manifold.a/b` or `vehicle.chassis`. `make()` (`:803`)
   allocates `count × size` from the file before `IO_LIST` compares count
   with the buffer (`:883`); `sec_wind` zero-fills up to 16 GB on a bad
   `grid_n`. A corrupt save passes `f3d_world_restore` and reads out of
   bounds on the first step instead of the promised "refused, world as it
   was". No fuzzing of any decoder exists.
3. **S1, read.** MCP file tools take paths straight into `File()` with no
   root: `flutter3d_mcp/lib/src/model/model_tools.dart:1269, 3059, 3083, 3125, 3180`,
   `editor/editor_session.dart:410`, `kit/capture_files.dart:117, 138`,
   `flutter3d_sim_mcp/lib/src/sim_session.dart:73, 549`;
   `diagnostic_renderer.dart:153` accepts absolute paths and `..` from a
   level file. `play_session.dart:39-44` and `flutter3d_editor_play/lib/src/flutter_run.dart:31`
   run with `runInShell: Platform.isWindows` and put the `device` string
   from `editor_tools.dart:459` into `-d <id>` unvalidated. The loopback
   transport is sound (token, per-request check) but accepts the token in
   `?token=`, compares with `!=`, has no body limit and writes the session
   file with default permissions (`kit/loopback_http.dart:136-237`).
4. **S2, read.** `flutter3d_net/bin/relay.dart:94` listens on `anyIPv4`
   with no authentication and no cap on watchers; the accept loop awaits
   each upgrade. `peer_room.dart:137` drops a hello without a `body` before
   parsing, so an old peer waits forever instead of reading "update to N".
   `rollback_session.dart:258` `_early[from][at]` is unbounded.
5. **S2, read.** WebGPU keeps shader and validation errors in `_errors`
   (`flutter3d_webgpu/lib/src/webgpu_device.dart:524`) that only
   `debugDrainErrors` (`:740`) reads, which production never calls; no
   `uncapturederror` listener. `_guard` (`:713`) appends a Future to
   `_pending` on every pipeline, pass submit and present, drained only in
   the same debug call: a leak of several entries per frame.
6. **S2, read.** Impeller and CPU do not override `lost`/`isLost`
   (`flutter3d_hardware/lib/src/graphics_device.dart:790`), so a context
   loss on Android/iOS goes unnoticed; WebGL shader compile failure is a
   `StateError` (`webgl_shaders.dart:160, 342`); a missing asset is a
   `StateError` or raw `FlutterError` (`flutter3d/lib/src/engine/assets/load_model_asset.dart:202`,
   `bundle_asset_source.dart:32`) with no `AssetNotFound` type among 31
   typed exceptions.
7. **S3, read.** Wasm plugin `restore` of a corrupt state throws
   `RangeError`/`TypeError` (`flutter3d_plugin_runtime/lib/src/wasm/interpreter.dart:390-408`)
   instead of `WasmFormatException`. `FormatSpec.versionOf` reads
   `"version": 0` and negatives as 1 (`flutter3d_foundation/lib/src/formats.dart:153`);
   `SettingKey<int>.decode` throws on `1e999` against "never throws"
   (`flutter3d_game/lib/src/config/game_config.dart:43`).

### 2.5 Boundaries

All nine rules of `1.0-boundaries.md` are implemented and green; moves 1–14
are in the tree; there are no cross-package `src/` imports in `lib/`, no
Flutter in the 22 plain-Dart packages, no layer inversions by pubspec.
What the rules do not see:

1. **S2.** The demos' hooks import `flutter3d_build` (a dev dependency)
   and `hooks` (undeclared): `apps/flutter3d_demo_{dungeon,platformer,racing}/hook/build.dart:1-2`.
   A hook may only import `dependencies:`; this drags `flutter3d_build` →
   `flutter3d_mcp` → `dart_mcp` into a game build.
2. **S2.** `apps/flutter3d_lesson_viewer/lib/main.dart:29` and
   `apps/flutter3d_stereo_lesson_viewer/lib/main.dart:41` import
   `flutter3d_editor_core`; both are runtime viewers. Rule 7 covers
   packages, not apps.
3. **S2.** `plugin_runtime` still hardcodes `'materials'`, `'renderSteps'`,
   `'entityKinds'`, `'shaders'` (`data/data_sections.dart:30-39`,
   `data_plugin.dart:128, 413, 500, 588`) and therefore depends on core,
   sim, shaders, physics and hardware, which puts the render core on a
   replay server. Move 14 is half done.
4. **S3.** Views read the simulation directly past `published`:
   `flutter3d_effects/lib/src/elements.dart:283` exposes
   `NativeWorld get world => simulation.world`; `demo_reef/lib/main.dart:611`,

1. **S2, read.** Per-draw allocations on every backend: a new
   `ByteData`/`Float32List` per uniform block bind

   `webgl_encoder.dart:821`), 6–10 blocks per mesh per view including

### 2.9 What a plugin can reach in the frame (audit of 2026-10-09, later the same day)

Paths: **R** = `flutter3d_core/lib/src/engine/render`, **F** =
`flutter3d_core/lib/src/formats`, **P** = `flutter3d_plugin_api/lib/src`,
**PR** = `flutter3d_plugin_runtime/lib/src`, **H** =
`flutter3d_hardware/lib/src`.

**The frame's skeleton is sound.** Every engine pass sits in a slot behind
an anchor (`_FrameSchedule.stage`, R/renderer.dart:3028-3231); a plugin adds
a `RenderNode` at an anchor (`RendererSteps.addNode`, R/renderer_steps.dart:155),
its own anchor (:238), a contributor (:277), replaces a stage by name
(`addMaterials`, :426), switches an engine step off (`provide`, :326, or
`RenderSettings.without`), and reads an engine output by `ResourceId`
through `FrameResources` (R/frame_resources.dart:269-377) after declaring
`reads`. `RenderNode`, `PassContributor`, `RenderStepAddon`,
`LightingModelAddon`, `ShadowTechnique`, `RenderServices` are
`abstract base` with defaults; `PluginApiVersion` 1.0 major-matches
(P/version.dart:52). Full-screen post stages work at every anchor on every
backend. Lit models through `.f3dmat` `light/ambient/composite/vertex`
plus `LightingModelAddon` (R/lighting_model_addon.dart:85) draw inside the
scene, the probes' captures and the transparency pass.

**By backend.** Impeller: plugin shaders only from a bundle; the runtime
refuses (PR/data/runtime_shaders.dart:260); a plugin may ship its own
`.shaderbundle` and `device.loadShaders` it (R/lighting_model_addon.dart:72,
`gpu_device.dart:264`), tied to the SDK that built it, which no page
documents. WebGL2: everything at run time. WebGPU: run time is an Unlit
splice (no `light`, `vertex`, `sceneDepth`; PR/data/material_wgsl.dart:67),
full-screen yes, compute no. CPU: everything, `compute` included.

**Where a real plugin stops (by weight):**

1. **Impeller without a build hook.** No published contract for a prebuilt
   bundle per plugin; data plugins get no rendering on Impeller at all.
2. **A lit model with its own BRDF** (hair, cloth, subsurface) cannot add
   uniform blocks or textures beyond the engine's five slots
   (material-language.md:45), a G-buffer channel or a shadow lookup
   (R/shadow_technique.dart:150-157); WebGPU run time refuses `light`.
3. **A new light type.** `LightType.custom` draws "as base"
   (scene/light_node.dart:20-27); the light loop and the packed list are
   the engine's (R/pass_contributor.dart:550-576), with no hook.
4. **A shadow technique of its own.** Only cascades, kernels and a
   prefilter stage (R/shadow_technique.dart:85-185); the cube atlas is
   outside the technique (:160); `shadow_map`'s producer cannot be replaced.
5. **A TAA-like post effect.** Depth yes, history yes (`keeps` + `provide`,
   R/frame_graph.dart:133), **velocity only when TAA or motion blur is
   on** (R/renderer_frame_nodes.dart:1982), and `FrameContext` carries no
   previous view-projection (`FrameHistory` is internal,
   R/frame_history.dart:316).
6. **A decal with its own material.** The decal stage is fixed, 16 decals
   and 4 textures (R/renderer_decal_pass.dart:24-27).
7. **GPU particles.** A `RenderNode` with `beginComputePass` and
   `provideBuffer` works on WebGPU and CPU; Impeller and WebGL2 refuse
   `DeviceFeature.compute` (H/graphics_device.dart:498-504); `.f3dmat
   compute` is CPU-only.
8. **A new vertex attribute or layout.** A plugin vertex stage is allowed
   (F/lighting_model.dart:287) but the layout is what the stage declares
   (device_mesh.dart:61); instanced and lightmapped stay engine stages.
9. **MRT or a new target format.** A plugin's own pass yes (up to
   `maxColorAttachments`); the engine's scene MRT (3 attachments) is
   closed; `declare` from inside `execute` works but is undocumented.
10. **Per-view (stereo).** `FrameContext.view` is the first view only
    (R/render_node.dart:82-84); no view index, no per-view resources.
11. **Culling and sorting.** `OcclusionTest` can be replaced
    (R/renderer.dart:1799); frustum, `RenderList` and the sort key are closed.
12. **Readback.** `device.readback` from a node works (H/graphics_device.dart:442).

**Stability risks in these APIs.** `MaterialExpression`,
`MaterialStatement` (F/material_language/material_ast.dart:631, 736) and
`ResourceSize` (R/resource_desc.dart:6) are `sealed`: a plugin cannot add
an expression and a new node breaks outside switches. The hardware enums
(`StorageMode`, `LoadAction`, `CompareFunction`, … H/formats.dart) are
closed while `TextureFormat` is open. String ids with no namespace:
`RenderStep.name`, `RenderNode.name`, `SettingsSlot.id`, `ResourceId`,
`LightingModel.shaderName` (case-insensitive, :488-497), `RenderAnchor`
(the doc promises `<pluginId>.<name>`, P/render.dart:43, `addAnchor` does
not check); only `FormatRegistry` enforces the prefix (P/formats.dart:161).
`LightingModels` is a process-global static registry
(F/lighting_model.dart:468). `static const` limits in the shader ABI:
16 decals, 8 lights per contributor (R/pass_contributor.dart:552),
`materialDepthLayerLimit`, `ExposureMeter.size`. Nullable "unsupported":
`ContributorFrame.viewProjection/sceneDepth/lights` (:399-429),
`LightingModelAddon.stagesFor → null`. Three entrances for stages
(`addMaterials`, `extraBundles`, `stagesFor`) and two ways to switch off.
**`ShaderStageNeed` does not exist** (decision 17 assumed a declaration;
today only `LightingModel.uses*` flags, `BundledMaterials.lighting` and
`RenderStep.passes` say what a stage needs). Conformance checks nothing of
rendering (`plugin_checks.dart:22-27`). Wasm plugins reach data and
simulation only (PR/wasm/abi.dart:57-61). No texture-codec registry (KTX2
and Basis are wired in). `FramePacing` and `AdaptiveQuality` are `final`
with no hook; `SkinBlend` is closed; LOD has data but no policy.

### 2.10 A fifth backend from outside (audit of 2026-10-09, evening)

The owner's requirement: a HAL backend for another platform or API
(Vulkan or Metal through FFI, Direct3D, a headless server renderer) must
stay writable outside this repository and plug into apps, the engine, the
conformance suite and the testing package without a fork.

**Verdict: possible today, through to a green `runDeviceConformance`.**
`GraphicsDevice` is `abstract base` with the promise "implementable
outside, stays so through 1.x" (`flutter3d_hardware/lib/src/graphics_device.dart:42-47`),
every feature-gated device member has a default body (`:486-760`); the
handle constructors are public in `backend.dart`, which is in the API
snapshot (`api/flutter3d_hardware.api:5-23`); `DeviceRegistry.addBackend`
and `addPresenter` make a fifth backend the preferred one without editing
`flutter3d_app` (`device_registry.dart:57-96`, the Impeller and WebGL
registrations live in their own packages); `FramePresenter` is a public
function typedef (`scene_surface.dart:18-24`); `DeviceLoss` is handled
generically (`flutter3d_view.dart:552-586`); the conformance runner is
public and needs only a device factory (`flutter3d_conformance.dart:113, 212`);
`DeviceClass` comes from traits, not names; "report unsupported" is a
documented, tested path (`checkCapabilitiesAreHonest`).

**What needs a fork today:**

1. **Plugin materials.** `RuntimeShaders` switches on cpu/webgl/webgpu/
   impeller and refuses the rest (`flutter3d_plugin_runtime/lib/src/data/runtime_shaders.dart:84-276`);
   the build hook hardcodes four bundle sections
   (`flutter3d_build_hooks/lib/src/material_compile.dart:318-332`,
   `material_build.dart:141-145`). A fifth backend gets no `.f3dmat`.
2. **The encoders break the HAL's own promise.** `PassEncoder` has 38
   abstract members, three with bodies (`command_encoder.dart:122-588`);
   `ComputeEncoder` (`compute.dart:125-225`) and `TransferEncoder`
   (`transfer.dart:53-135`) likewise, feature-gated ones included. The
   README promises "a member without a default body waits for a major"
   (`flutter3d_hardware/README.md:64-80`); a minor that adds an encoder
   member breaks every outside backend.
3. **The engine's goldens are CPU-only.** `flutter3d_testing.renderFrame`
   and `testReplay` open `cpuTestDevice` (`render_frame.dart:66`,
   `test_replay.dart:266`); `drawOnce(device:)` is deliberately not
   exported (`draw.dart:7-11`).
4. **Shaders.** The device receives an F3SB bundle with open string keys
   (`shader_bundle.dart:56-65, 164-171`), so a `'vulkan'` section is
   possible, but `compileStage` keeps SPIR-V in a temp dir and returns
   WGSL only (`wgsl_compiler.dart:68-140`); `stageBindings` and
   `uniformBlocks` sit in `flutter3d_shaders/internal.dart`, declared
   outside semver; the 105 required entry points
   (`flutter3d_shaders.dart:41-148`) and the `F3D_*` defines are not in
   CONTRACTS.
5. **The guide is 0.8.** `site/content/core/backends.md` shows `supportsX`
   getters, `abstract interface class PassEncoder`, `present`/`readPixels`
   and a nullable `createTextureFromPixels`; the hardware SKILL likewise.
   README:6-8 still says "three implementations".
6. **A rule that never fires.** "every package that implements
   GraphicsDevice is named in SUPPORT" greps `implements`
   (`tool/structure/detectors.dart:983-986`); every backend writes
   `extends`, as a `base` class requires.
7. **Conformance counts refusals two ways:** `decline()` → skipped in some
   checks, a silent `return` counted as pass in others
   (`core_checks.dart:327, 448`, `stencil_checks.dart:33, 200`,
   `render_target_checks.dart:31`, `draw_checks.dart:362`).
8. No minimal outside backend exists; `FakeBackend` overrides ~45 members;
   `flutter3d create plugin` has no `backend` kind.

**The rc.1 plan's HAL changes, seen from outside.** Additive: one `open`
shape (`BackendOpener` already has it), `Recorded` → base,
`releasePipeline`, async pipelines. Breaks, allowed because rc.1 is the
last free break but to be labelled for outside implementers: moving
`readBufferSync` to `testing.dart`, folding `createStorageBuffer` into
`createBuffer(usage:)` (a backend that overrides only the old one silently
loses storage buffers), `decodeTexture` non-null, typed presenters, the
dispose checks, `DeviceLoss` as an obligation, `MissingShaderStage` when a
bundle may be partial.

### 2.11 The public surface against other engines (2026-10-09, evening)

Two readings, one of twelve engines' public APIs and their regrets, one of
flutter3d's own surface along the same axes. The target was set first:
declarative widgets over an imperative core, Dart and data plugins equal,
many packages behind two facades, and the power of extension winning a
conflict. Sources are the official docs and sources as of the day; the
agent's notes hold the URLs.

**Where flutter3d already follows what the well-regarded engines share.**
One registration object with a build hook (Bevy `Plugin::build`, Kit
`IExt`, USD `plugInfo.json`) — `Flutter3dPlugin.install` with registries
asked for by type. A manifest versioned against the contract, not the
engine (Godot `compatibility_minimum`, O3DE `api_versions`, bgfx
`bgfx_get_interface(version)`) — `PluginApiVersion` with its own line, and
`simulationVersion` in the manifest feeding `SimulationVersion.plugins`,
which no engine on the list does. Named insertion points rather than
positions (URP `RenderPassEvent`, HDRP injection points, Godot
`CompositorEffect`, Unreal `SceneViewExtension`) — 25 anchor pairs. A
material as a declaration plus one surface function compiled per backend
(Filament `.mat` + `matc`, O3DE `.materialtype` + AZSL, flutter_scene
`.fmat`) — `.f3dmat`, with an open lighting-model registry where Filament
has five fixed shading models. An explicit sim/render boundary with a
snapshot (Unreal proxies, Bevy extract, O3DE feature processors) —
published state, with the loop itself refusing `world` in frame phases.
Capabilities as flags (wgpu `Features`/`Limits`/`Downlevel`, bgfx `Caps`)
and a conformance suite per backend (wgpu CTS) — `DeviceFeature`,
`checkCapabilitiesAreHonest`, `runDeviceConformance`. A backend
implementable outside through the same path as the engine's own (O3DE RHI
Gems, Hydra render delegates, gz-rendering plugins, `wgpu::custom`) —
`flutter3d_hardware` base classes and `backend.dart`; bgfx, Stride, Godot
and wgpu-hal cannot. Physical light units and camera exposure (Filament,
HDRP, Unreal, O3DE) — lux and candela by contract. Units and handedness in
one document (Godot, O3DE, Unreal) — CONTRACTS; Bevy, PlayCanvas, Filament
and three.js never wrote theirs down. Import as a plugin with a format
registry (USD `SdfFileFormat`, Godot import plugins, Bevy `AssetLoader`)
— `FormatRegistry`, `ModelDecoders`, `convert`.

**The regrets flutter3d avoids by construction.** Bevy's break every
three months and the render graph deleted in 0.19 — strict semver from
1.0 with API snapshots. Unity's three pipelines with incompatible shader
libraries and a converter that cannot carry custom shaders — one material
for four backends. three.js `onBeforeCompile` string patches, replaced by
TSL — no string patching. Babylon's left-handed default and its mirrored
glTF root — right-handed Y-up from the first day. Godot 4.0 → 4.1
breaking GDExtension binaries — the C core is internal, the promise is on
Dart. Unreal without semver, vendors rebuilding on every minor — snapshots
and migrations. Filament's closed frame graph and "use tools from the same
release" — the graph is open. Stride promising no breaks in minors and 4.4
breaking anyway — the rules run in CI. PlayCanvas 2.0 deleting
`Layer.onPreRender` and asking users to write GLSL and WGSL by hand — one
GLSL translated. USD's `metersPerUnit = 0.01` default — metres, stated.
flutter_scene at 0.x with "a minor can break", a winding change in 0.23
and a backend chosen at compile time — the opposite on each point.

**Where the comparison found flutter3d thinner, and what was decided.**

| Pattern elsewhere | flutter3d today | Decision |
|---|---|---|
| A declarative pipeline file (O3DE `.pass`/`.azasset`, Stride's compositor asset, Babylon `NodeRenderGraph`) | the graph is assembled in code; data plugins reach only `renderSteps` | **43**: `f3d.pipeline` document |
| Transient resources declared to the graph, memory by lifetime (Unity `CreateTexture` + culling, RDG transient allocator, O3DE `Lifetime`) | `declare` inside `execute` | **37**: `setup(FrameGraphBuilder)` |
| A material type with a version and parameter updates (O3DE `versionUpdates`, PlayCanvas `shaderChunksVersion`) | the language is versioned, a material is not | **44**: `version` and `updates` in `material {}` |
| Plugin groups with overrides (Bevy `DefaultPlugins.set(..).disable::<X>()`) | a list of addons | **45**: `PluginGroup` with `set`/`with`/`without` |
| One way to write a system (Bevy systems with ordering, Stride processors) | two APIs | **35** |
| Component → render mirror (Unreal proxies, Bevy extract, Unity Entities Graphics) | hand-written per view | **36**: `SceneBinding` |
| Typed material parameters (Filament `setParameter`, Bevy `AsBindGroup`) | a string map with generated accessors | **38** |
| Editor extension (Godot `EditorPlugin`, Omniverse Kit) | commands and MCP only | **31** |
| Render thread or pipelined rendering (Unreal, Filament, Bevy) | the step on the UI isolate by default | **40**: a placement setting |
| Deprecation with a named removal version and a migration tool (Unity API Updater, Godot, three.js "ten releases") | planned | **14**: none in 1.0, `dart fix` after |

Not adopted, with the reason: Bevy's ECS-first scene (the scene graph is
the view and `SceneBinding` bridges it); Unreal's and Unity's node
material graphs (the roadmap's "texture compositor, not a shader graph"
stands; `.f3dmat` is text, as Filament's and O3DE's are); Babylon's
"deprecated is never removed" (a major removes, with migrations); USD's
`YY.MM` versioning (semver); Godot's experimental multithreaded servers
(one placement setting instead).

## 3. The target state of rc.1

What the tree looks like when the candidate can be tagged, given the three
decisions above.

1. **Correct under rollback and across machines.** Every component that a
   system reads after a restore is either in the snapshot or has an
   `InPlaceCodec`; a restore replays the origin shift through the same
   hooks as a live shift; a genre part of nothing is not "restored"; a
   newer codec version, a tape without a version and a hello without a
   body are refused with a sentence; no simulation code reaches libm
   through `vector_math` (the rule reads the AST or bans the specific
   constructors). The C core refuses a corrupt snapshot before touching
   it, and both decoders have a fuzz test in CI.

   validated token; the relay has an owner token and caps; WebGPU drains
   errors every frame and listens for `uncapturederror`; Impeller and CPU
   report loss; a missing asset, a failed shader and an unsupported format
   are typed exceptions under `Flutter3dException`.

   implementable interface or a growing result; `sealed` only on
   result-like sets; light, shadow and material kinds as open classes;
   one `open` shape on every backend; colours are `LinearColor` in every
   public signature including `Level`; load/decode/parse throw; nothing is

   `readBufferSync` is in testing; the limits are getters; the

## 5. For thinking and elaboration

Open questions the review raised. All eleven were decided the same day;
§6 has the decisions and the work they add.

1. **Precision strategy for 1.x.** The contract says `WorldPosition` is
   double and the scene is a floating origin, but nothing shifts it, nodes
   and bodies are Float32, and the C core is `float`. Three honest options:
   (a) document a world limit (about 1–2 km from the origin) in CONTRACTS
   and SUPPORT, with a test at the limit, and leave shifting to 1.x;
   (b) make `Flutter3dView` shift the origin automatically when the camera
   passes a threshold, which exercises the hooks found broken above and
   needs the hashed-noise fix; (c) a `vector_math_64` scene layer, which is
   the largest change and touches ~1 100 imports. (a) is honest for rc.1;
   (b) is what the API already promises; (c) is a 2.0 question. Whichever
   it is, the Dart-vs-native digest should either be compared in a test or
   the two engines declared separate simulations with separate
   `SimulationVersion`s.
2. **Resource ownership on Impeller.** Plan item 20 asked for reference
   counts and a leak rule; the tree has one cache with a refcount and
   empty `dispose` on Impeller because flutter_gpu has no release. Either
   the 1.0 promise is "handles are owned by the device and released on
   `dispose`, which on Impeller means GC", written into the HAL doc and
   SUPPORT, or an upstream request for `gpu.Texture.dispose` is filed and
   the promise waits. A leak rule that counts live handles in the fake
   backend across a test is cheap and worth having either way.
3. **What `sealed` means in this API.** The audit found 26 sealed sets;
   the policy "sealed only where the user is meant to switch and the set
   is closed by definition" would make a structure rule with an allowlist.
   Decide the list once rather than per review.
4. **Entry points.** Three ways in (`Flutter3dView`, `Scene3D`,
   `SceneSurface`), three sources (quickstart, scaffold, demos) each
   starting from a different one. One of them is the first page; the
   others are explained as what it stands on. The demos are the strongest
   teacher and today teach `SceneSurface` plus `openDevice`.
5. **Hot-path allocations before or after 1.0.** Scratch buffers per
   uniform block and a cached compiled frame graph are internal and could
   land in 1.0.1; but if the per-frame telemetry cannot be switched off,
   `RenderSettings.telemetry: off` is an API addition better made now.
6. **The shader bundle.** 8.5 MB in every binary and 5 MB of shader text
   in every web build is the cost of one bundle for all; a per-app
   selection (only the stages a project's materials name, computed by the
   build hook) is additive and would change the quickstart's size story.
7. **The nightly.** Decision 14 of `1.0-stability.md` and the roadmap both
   promise an Impeller nightly on real hardware; nothing schedules it.
   A self-hosted runner or a documented manual cadence, but written down.
8. **History.** 158 unpushed commits, a rewritten history in a backup,
   and a tag to make. Tagging before the force-push means the tag's commit
   may not exist afterwards. The order should be: force-push, re-base the
   branch, then tag.
9. **The demos as examples.** Six of nine games still carry numbers the
   core does not have (hazard tables, brand dice, crash thresholds, hand
   masses). Users read the demos as the API. Either finish
   `0.9-no-crutches.md` or label each demo's crutch in its README as a
   crutch.
10. **Own-line packages and pre-releases.** `flame_multiplayer` on
    `flutter3d_net ^1.0.0-rc.1` cannot be a release while net is a
    candidate. Either the four own-line packages follow the engine's
    candidate (`0.3.0-rc.1`), or they wait for 1.0.0 and are published a
    day later, which `1.0-publish.md` should say.
11. **Audio and the world.** `speedOfSound` from temperature exists and no
    consumer reads it; the same is true of cloth. Before adding more world
    properties (humidity, ozone), decide that every property has a reader
    on the day it is added, which a structure rule can hold (a property
    with no reader outside matter fails).

## 6. Decisions of the second round (Dmitrii, 2026-10-09)

The engine is for games, digital twins and virtual laboratories alike.
Sixteen questions were put on that basis; the answers below are the
decisions, each with the work it adds to the list in §4.

### Foundations

1. **World precision: the view shifts the origin itself.** `Flutter3dView`
   rebases the world when the camera passes a threshold (about 1 km),
   through the existing hooks, which wave 1 repairs. The contract
   documents precision relative to the camera, not to the origin. The
   hashed-alpha noise is anchored on world position plus origin so a
   rebase does not re-roll it. A `vector_math_64` scene layer is a 2.0
   question.
2. **Time: one loop, an abstract source.** `EngineLoop` keeps the fixed
   step; a `TimeSource` drives it: real time, scaled ×N, a telemetry log
   with timestamps, a manual step for a laboratory. Determinism holds;
   adaptive integrators live inside a step.
3. **Two explicit accuracy profiles.** `SimulationProfile.deterministic`
   (Portable maths, float-compatible, rollback, one `SimulationVersion`)
   and `SimulationProfile.accurate` (double, adaptive integrators,
   analytic tests, no cross-platform bit promise). A game picks the first,
   a laboratory or a twin the second; each has its own version.
4. **Twins stay outside; the engine promises the hooks.** The twin package
   lives in its own repository and is written against: the time source,
   external state as input, probes, geo-referenced origin, materials with
   external ids.

### Materials and measurement

5. **Every material property is a function of state** (temperature,
   pressure, phase); the 20 °C scalar is the value of that function at the
   reference state. The field type in 1.0 is the law, not the number, so
   readers call `at(T, p)` from the first release.
6. **Where the law is evaluated: a hybrid by group.** The thermal and fluid
   groups are evaluated in the C core, whose header carries their tables
   and coefficients, because their consumers (heat, fire, liquids) are
   there; the mechanical, optical and acoustic groups are evaluated in
   Dart and pushed as scalars when the state changes beyond a threshold.
   The two interpolators must agree bit for bit, which a parity test
   holds.
7. **Identity: own id plus a map of external ids.** `PhysicalMaterial`
   carries `externalIds` (CAS, IFC, MaterialX, …); the catalog looks up by
   any space; converters bind by them and report what they could not
   bind. The source stays a required field of every value.
8. **Probes are simulation components.** A `Probe` is declared in the
   simulation (a point, a section or a body, and a quantity with its unit),
   read in the `publish` phase, carried in `PublishedState` and on the
   tape, with a codec. Views and charts read only that. This closes the
   direct `run.world` reads in the demos.
9. **Telemetry is input with a timestamp.** External state (MQTT, OPC UA,
   a log) enters as an `InputFrame` of its own kind, goes on the tape and
   replays; an assimilation system inside the step decides between the
   sensor and the model. The boundary does not change.

### API policy

10. **`sealed` and `enum` only for sets closed by definition**: operation
    results and GPU constants, on an allowlist with a reason, held by a
    structure rule. Everything the engine or a plugin can extend (light,
    shadow and material kinds, shapes, commands, bindings, material
    expressions) is an open class with a wire name, as `LightType` is.
11. **`Flutter3dView` is the one way in, and every demo moves onto it in
    rc.1.** It owns the device, the loop and the time source; input, saves
    and rollback are plugins a laboratory does not install. `Scene3D` is
    declarative sugar on it; `SceneSurface` is the documented lower layer.
    The 34 parameters are grouped into owner objects.
12. **`flame_multiplayer` and `flame_multiplayer_dashwire` join the
    engine's number**, `1.0.0-rc.1`, since they stand on net and
    plugin_api and break with them. Only `pad_input` and `pointer_lock`
    keep lines of their own.
13. **Ownership: explicit `dispose` everywhere, honest about Impeller.**
    Every handle has an owner and a `dispose`; double dispose and
    use-after-dispose are debug errors; a rule counts live handles in the
    fake backend after each test. SUPPORT says that on Impeller memory
    returns through the collector, and a request to flutter_gpu for a
    native dispose is filed. Reference counts stay in `ResourceCache`.
14. **No `@Deprecated` in 1.0.0.** All eight go before rc.1; the old names
    live in the migration table and `fix_data` only; a rule forbids
    deprecations in a major release.
15. **The hot-path work goes into rc.1 in full**: `RenderSettings.telemetry`
    (off, counters, timings), `warmUpInSlices` called from `Flutter3dView`
    after the device opens, scratch buffers per uniform block, a cached
    compiled frame graph, and a draw-count and allocation benchmark in CI.
16. **`0.9-no-crutches.md` is finished in rc.1.** No number in a demo that
    the core does not have; the engine copies in demos (`ElementSounds`,
    `OpenKind`, `LessonPlayer`) are deleted and a rule forbids a demo
    declaring a class whose name a package exports.

### The questions left open in §5

17. **The shader bundle is selected per project by the build hook.** The
    `flutter3d_build` hook collects the stages a project's materials,
    `RenderSettings` and plugins name and writes the Impeller bundle and
    the web shader maps from those alone; the full set is a flag and the
    editor's default. The shape that must be in rc.1: how a stage declares
    that it is needed, and how the runtime refuses a missing stage with a
    typed exception naming it.
18. **A self-hosted macOS runner runs the Impeller goldens nightly.**
    Dmitrii's Mac as a GitHub Actions runner with the label `impeller`; a
    `schedule:` job runs `golden.sh`, the conformance suite and pacing,
    uploads the diffs as an artefact and feeds a "nightly" badge in the
    README. SUPPORT says it runs only while the machine is on.
19. **History first, then the waves, then the tag.** The rewritten history
    in `~/backups/purge-work.git` is force-pushed before any wave is
    committed; the 158 commits and the working tree are carried onto it;
    each wave commits by area and pushes; `v1.0.0-rc.1` is the last thing
    made. No new commit goes onto the old history.
20. **A property with no reader is a scan error.** Every public property
    of `WorldProperties` and every group of `PhysicalMaterial` has at least
    one reader in the `lib/` of another package, tests and conformance not
    counting; a `Probe` counts as a reader. Adding a property means
    connecting its consumer in the same commit.

### The frame's extension points (after §2.9, the same day)

21. **The project's build hook compiles the plugins' materials.** The hook
    that selects shader stages (17) also compiles every installed plugin's
    `.f3dmat` into the project's bundle for the running SDK; at run time
    Impeller finds the stage by name or refuses with a typed exception;
    `doctor` checks. A plugin's own prebuilt bundle stays a documented
    option with an SDK check.
22. **Every extension point the audit names goes into rc.1** ("hooks to
    the maximum, now", Dmitrii): `velocity` as a step a plugin can ask for,
    with the previous view-projection and the view index in `FrameContext`;
    extra uniform blocks and textures for a plugin's lit model beyond the
    engine's five slots; a hook in the light loop for a plugin's light type
    and a replaceable shadow-map producer, cube atlas included; decals
    through a `LightingModel` with the limits as settings; a declared
    vertex attribute and layout for a plugin's vertex stage, instanced and
    lightmapped variants included; plugin-declared resources and MRT
    outputs as a documented API, not a side door of `execute`; per-view
    resources and a view list for stereo; a hook into `RenderList` building
    for a plugin's culling and sort key; a `TextureCodecRegistry` beside
    the model decoders; a LOD policy hook; a skinning hook beside
    `SkinBlend`; a frame-pacing hook on `FramePacing` and `AdaptiveQuality`;
    compute steps through the frame graph on the backends that have
    compute, with a typed refusal on the others; `.f3dmat compute` on
    WebGPU. Wasm plugins get the data plugin's render surface (steps,
    materials, effects); a native render ABI for Wasm is the one item left
    to 1.x.
23. **Every plugin-registered name carries `<pluginId>.`**, built-ins
    `f3d.`: anchors, steps, nodes, settings slots, lighting models,
    resource ids. A violation is a `PluginException` at install. The
    registries belong to the engine instance, not the process; names
    compare case-sensitively. A structure rule and a conformance check
    hold it, and conformance gains render checks: a plugin that registers
    a step or a lit model passes on all four backends.
24. **The material AST opens**: `MaterialExpression`, `MaterialStatement`
    and `ResourceSize` become `abstract base` with a visitor whose default
    is `visitUnknown`, so an outside translator survives a new node and a
    plugin may add expressions. `materialLanguageVersion` still names what
    a translator supports.

### A fifth backend from outside (after §2.10, the same day)

25. **The HAL stays implementable outside, and rc.1 proves it.** Into rc.1:
    a material-compiler SPI per backend (a backend registers its `.f3dmat`
    compiler and its bundle section with `RuntimeShaders` and with the
    build hook); default bodies on every feature-gated encoder member,
    held by a rule "a new HAL member arrives with a body"; the shader
    contract for a backend author (`compileStage` returns SPIR-V and takes
    a target language, `stageBindings` and `uniformBlocks` in a public
    library, the 105 entry points and the `F3D_*` defines in CONTRACTS);
    `flutter3d_testing` takes a device; one `decline()` in conformance;
    the guide and the SKILL rewritten for 1.0; a sentence on
    `backend.dart`'s stability; the `implements`→`extends` rule fixed.
26. **The reference outside backend lives in this repository, outside
    `packages/`**: `examples/flutter3d_backend_null`, a minimal headless
    backend that depends only on published libraries (a rule forbids it
    `internal`/`src`), passes conformance in CI, and is the template
    behind `flutter3d create plugin --kind backend`.

### Comparison with other engines (questions of 2026-10-09, evening)

27. **The target API style is declarative widgets over an imperative
    core**: `Scene3D` and its children for the first screen, twins and
    laboratories; `Flutter3dView` with `Scene` and `EngineLoop` for games;
    both first-class, one standing on the other. Packages stay many, with
    the two facades. When the comparison's recommendations conflict, the
    power of extension wins.
28. **Dart plugins and data plugins are equal, so data reaches every
    point.** Declarative points by data (`.f3dmat`, post stages, light
    types as curves and parameters, vertex layouts, LOD tables,
    substances, elements); points that need logic by the plugin's Wasm
    module, whose ABI covers the simulation step **and a render node**
    (encoder commands through `Recorded`). This overturns "a native
    render ABI for Wasm is 1.x" in decision 22: it is rc.1.
29. **OpenUSD is the interchange for twins, `.f3d` the runtime.** In 1.0
    the USD import carries primitives, materials (UsdPreviewSurface and
    MaterialX), the hierarchy and custom attributes into prefabs and
    levels; export to USD is 1.x; IFC comes through a converter later.
    The Hydra render-delegate model is the comparison for the HAL.
30. **Laboratories on two levels.** An experiment is a document (a level,
    its substances, probes and a scenario) a teacher edits in the editor
    or an agent through MCP, with no code, as PhET and Algodoo do; new
    instruments and laws are Dart, as Labster's are code.

31. **The editor is part of the plugin contract, in full, in rc.1**: a
    plugin's components, materials and entity kinds get an inspector from
    their hints; a plugin registers commands (the same the MCP server
    calls), gizmos, importers, panels and docks, and entries in the asset
    browser, as Godot's `EditorPlugin` and Omniverse's Kit extensions do.
32. **One expression language for everything.** The `.f3dmat`
    expressions, with units, become the engine's expression language,
    living in `flutter3d_foundation` with a deterministic evaluator
    (Portable maths): `PropertyLaw`, derived probes, scenario conditions
    and force fields in an experiment are written in it, with no code.
    `.f3dmat` stands on it.
33. **One source, N viewers is a 1.0 promise.** A twin or a laboratory is
    an authoritative simulation with its input tape (telemetry included);
    viewers replay it through the relay's observer path. The `accurate`
    profile ships poses, not a resimulation.
34. **WCAG 2.x AA for `game_ui` and the lesson viewers**: `textScaler`,
    reduced motion, `Semantics` on every control, contrast by tokens, no
    flashes above 3 Hz; a structure rule and an accessibility test in CI.
    The demo games are best effort.

35. **One way to write a system.** `host.loop.addSystem(name, LoopPhase,
    fn, after:)` with `LoopContext` is the API; `StepSystems`/`StepContext`
    with `begin`/`end` go before rc.1, and the genres and the elements move.
36. **A declarative bridge from published state to the scene.**
    `SceneBinding`: a plugin, a game or a `Scene3D` widget declares that
    an entity with component X is drawn as a node of a kind with a
    material; the engine creates, updates, interpolates and removes the
    nodes from `PublishedState` every frame, as Bevy's extract phase and
    Godot's `RenderingServer` do. The same binding is reachable from a
    data plugin. `actor_visuals.dart` is rewritten on it.
37. **A setup phase in the frame graph.** `RenderNode.setup(FrameGraphBuilder)`
    declares resources, reads and writes before the frame; `execute` only
    draws; declaring inside `execute` stays for dynamic cases, as an
    exception. The engine can then alias and bound the lifetimes of
    plugin resources as Unity's RenderGraph and Unreal's RDG do.
38. **Typed material parameters.** One `MaterialParameters` with
    `set<T>(ParameterKey<T>, value)` and `setNamed(String, Object)` against
    the schema the `.f3dmat` declares (type, unit, range, hint); the
    generated accessors stand on it; `Material3D` takes the same; the raw
    `Map<String, Float32List>` leaves the public API.

39. **`ScriptRuntime` goes.** The expression language and the Wasm module
    cover its cases; the `scripts` section of `.f3dplugin` becomes
    `expressions`.
40. **The simulation's isolate is one setting.**
    `Flutter3dView(simulation: SimulationPlacement.isolate)` hands out the
    same `SimulationHandle`; plugins with `touches: simulation` install in
    the isolate; conformance runs every genre and example in both
    placements; on the web the step stays on the thread and says so.
41. **Typed partial values.** `Level.world` is a `WorldPropertiesPatch`,
    `Level.renderSettings` a `RenderSettingsPatch`, each with a codec and a
    rule that every `Settings` field has a `Patch` field; `BackendId` is a
    value with constants for the four backends and a free name for an
    outside one.
42. **One entrance per thing.** A lighting model is registered only
    through `host.registry<LightingModels>()`; stages only as a
    `ShaderLibrary` through the same registry (`addMaterials`);
    `extraBundles` and `stagesFor` become its implementation, not API.

43. **A pipeline document.** `f3d.pipeline`, versioned: anchors, nodes
    with their resources (reads, writes, keeps), switched-off steps and
    settings slots. The engine's standard pipeline is written in it, so
    the fixture is the documentation; a data plugin and the editor edit
    it; `RendererSteps` is the same machinery under it.
44. **A material has a version and updates.** `material Hatch version 3 {
    updates { 2: rename ink -> inkColor; 3: scale roughness 0.5 } }`;
    instances in levels and `.f3d` carry the material's version and are
    lifted through the chain; the fixture rule covers materials as it
    covers formats.
45. **Plugin groups with overrides.** `StandardPlugins.set(BloomAddon(threshold: 1.2)).without<FogAddon>()`
    in `Flutter3dView(plugins:)`; standard groups for a game, a twin and a
    laboratory; the same for data plugins in the project document.
