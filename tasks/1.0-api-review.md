# The API surface before 1.0: extension points, seams, conventions

On 2026-10-08 Dmitrii asked for one more careful pass over the public API.
The question was where third parties extend the engine, where it meets
Flutter, the IDE, CI and agents, and what we would otherwise have to break
later.

Five reviews cover it:

- rendering and the HAL;
- simulation, physics and network;
- the game layer and addons;
- tooling, formats and plugins;
- conventions across all 71 snapshots.

This file brings them together. The questions for Dmitrii are at the end.
Once he has answered them, the decisions go into waves 3 and 4 of
`1.0-scope-additions.md`.

Each of the five reviews on its own reached the same conclusion: the
contract is not yet ready to freeze, and most of the fixes are mechanical.

## A. Principles for the 1.0 contract

These are the rules that every later item applies. Each one is checked by
a structure rule in `tool/structure.dart`.

1. **Whatever a user implements is an `abstract base class` with default
   bodies.** It is not an `abstract interface class`. That way a new
   member in a minor release does not break third-party implementations.
   Defaults throw `UnsupportedCapability` or do nothing. This covers:
   - `GraphicsDevice` and its encoders, `PhysicsBackend`, `RigidDynamics`,
     `CharacterMover` and `WorldRays`;
   - `AudioBackend` (which gains pause, resume and dispose), `Storage`,
     `CloudSaveStore`, `HeadTracker` and `ReplaySubject`;
   - `StepClock`, `ModelDecoder`, `ModelWriter`, the transports and
     `TelemetrySink`.
2. **Sets that will grow are open classes with constants, not enums.**
   This covers `LightType`, `TextureFormat`, `VertexFormat`, `QueryType`,
   `OutputTransform`, `ModelFormat`, `ColliderKind`, `RunOutcome`,
   `LevelLightType`, `GameState` and `RacePhase`.
   - A `sealed` modifier stays only where exhaustive matching is the point
     of the type.
   - Every sealed type in the snapshots gets an explicit decision.
3. **Anything written to a file uses explicit wire names.**
   - Today `CompareFunction.byName`, `TextureFormat.asNameMap`,
     `LevelLightType.name` and the trace values write Dart identifiers
     into files. The wave 4 renames would silently change file contents.
   - Wire-name tables must be in place before those renames.
4. **No global mutable state.** Registries belong to an engine instance.
   This covers:
   - `PhysicsBackend.current`, `LightingModel.registered`,
     `registerBackendOpener` and `registerDevicePresenter`;
   - `assetDeviceClass`, `maxDecodedTextureDimension` and `postGameEvent`;
   - the `Playing` globals and the `Gamepad`/`PointerLock.instance`
     singletons.
   This is required by the plugin model (two engines in one isolate) and
   by item 19 (a simulation in an isolate).
5. **No third-party types or private parameters in signatures.** This
   rules out:
   - the WebGPU JS types (240 lines of `GPU*`) and `WebGL*`;
   - `flutter_gpu`, `dart_mcp` (pre-1.0), and `Cubit` from `flutter_bloc`;
   - the 43 constructors that take `this._private`;
   - `@visibleForTesting` in public signatures.
6. **Backend and engine internals leave the snapshot.** This covers:
   - about 80 CPU shader classes and about 70 `*InfoBlock` types, plus
     `uniformBlocks`/`stageBindings`;
   - the renderer's 38 `*Shader` fields and its `debug*` members;
   - `RenderList`, `FramePassState`, `LightBuffer`, `Scene.register*`,
     `parity_scene`, and the `WasmModule` internals;
   - `RigidBody` and `CollisionWorld`.
7. **The demo games are not the engine.** These move to the apps or to an
   unpublished `flutter3d_samples`:
   - shooter's `sample.dart`/`crypt.dart` (where `Staged`/`stage` are
     defined twice) and strategy's `map_world.dart`;
   - `TorchFire`, `LevelWalk` and `AutomapView`;
   - the `String.fromEnvironment` constants and the repository hygiene
     helpers in `testing.dart`.
8. **No name collides with Flutter, `dart:ui` or vector_math, or with
   another of our packages.**
   - `Material` costs 100 `hide` clauses, `Ray` 34, and `Key` collides too.
   - These names are declared twice across our packages: `Pose`, `Body`,
     `FramePacing`, `ReadoutStyle` (three times), `KeyKind`, `ChaseCamera`,
     `Heightfield`, `ParticleSystem` and `Selection`.

## B. Extension points: one way for each kind

| What gets extended | Today | 1.0 |
|---|---|---|
| A render step | five ways: `addContributor`, `addNode(phase)`, `RenderNodeRegistry`/`FramePhase`, `RendererSteps.addNode(at)`, `FullscreenEffect` | One step node with a view-aware frame context (view, projection, jitter, time) that declares textures and buffers. Plugins may define their own `RenderAnchor`s |
| Lights, shadows | `LightType` closed, `ShadowFilter` private, `shadowedLights=6`/`maxLights=8` in the API | Open light types and a shadow-technique interface; the limits come from `DeviceLimits` |
| Genres | `PlatformerPlugin` registers `KeyKind` without a `kinds:` parameter, so two genres together throw at install | A `GenrePlugin<S>` base (`kinds`, `replaceKinds`, `headless`, `simulation`, `uninstall`); genre cameras on `VirtualCamera`; controllers as named `StepSystems` entries |
| Game reactions | `Reaction` is final with fixed lists | `ReactionEffect` + `ReactionBuilder.add` |
| Physics | `CollisionShape` sealed, `NativeJointType` closed | Capability interfaces `JointPhysics`, `ConstraintPhysics`, `ShapePhysics` (a custom shape with GJK support) |
| Formats | Version constants found by name pattern; three JSON envelopes | A `FormatRegistry` (id, suffixes, sniff, version, migrations, fixtures) that is also a `PluginRegistry` |
| Import and export | `builtInModelWriters` is a const list; the CLI does not accept third-party decoders | A `ModelWriters` registry, `convert --to`, `options` in `ModelLoadRequest`, a per-file `AssetImporter` under `BuildStep` |
| Editor | Only commands, components and palette entries; panels are a hard-coded list; `Handle` final, `Piece` a 3-value enum | `addPanel`, `addGizmo`, `addTool`; plugin commands visible to the editor's MCP server |
| Plugin names | `EditorPieces.add*` throws on a clash with a built-in, so a new built-in in a minor breaks a plugin | `<pluginId>.<name>` everywhere, as MCP tools already do |
| Plugin scope | `PluginTouches` has only `simulation`/`view` | Add `tooling`, so editor-only plugins don't ship in games |
| HUD and UI | Colours as constructor defaults; English strings as defaults | `GameUiTheme extends ThemeExtension`; `Flutter3dGameLocalizations`, or required text |
| Settings | `Map<String,double>`, a fixed set of panel sections | `SettingKey<T>`, `SettingsSection`; namespaced `SettingsSlot` ids |
| Saves | One slot, `save.json` | `SaveSlots`; the slot id already in `SaveFile` |

## C. Boundaries and integration seams

- **Simulation and view (items 17–19, 27).**
  - The view reads only `PublishedState`: immutable, built in `publish`,
    with double positions and the events of the step.
  - `SimulationHandle` gives `published`, `submit(input, seat)`, an async
    `query` and `rewindTo`. Its shape is the same in this isolate and in
    another one.
  - `Elements` splits in two. `ElementHook.step` runs over neutral
    `ElementFields`, and the view becomes a plugin over published state.
  - Simulation code does not import view types: `LevelLightType`,
    `CameraRig`, `Lightmap`, decals.
- **ECS.**
  - `LoopContext.world` (`SimWorld`) offers spawn, get/set, queries
    (with/without/changed), resources and deferred commands.
  - Every component has a versioned codec (item 30).
  - A `SnapshotRegistry` (id, version, capture, restore, digest) is the one
    path for `rewindTo`, rollback, replays and the editor's scrub.
- **`RenderView` (item 26).**
  - The name is taken today by a viewport descriptor.
  - The new view owns its target (texture or surface), its TAA history,
    its settings and a visibility hook. TAA history is keyed by
    `CameraNode` today, so stereo collides.
  - `RenderTexture` folds into it.
  - Its growing parameters go into a `RenderViewSettings` object from the
    start.
- **`Flutter3dView` (item 25).**
  - Focus, with `autofocus` off by default.
  - Input and `ActionMap` scoped to the view.
  - Lifecycle: `TickerMode`, routes, `AppLifecycleState`, and pause in
    audio.
  - `restorationId` mapped to a run snapshot plus a slot.
  - DPR policy, one audio listener per view, and an explicit owner for the
    device and renderer.
  - Stereo becomes this widget with two views, plus an XR session
    interface.
- **Network.** One transport (`send`, `listen`, `close`, `state`) and one
  N-player rollback on `EngineLoop`. `NetSession`, `RollbackSession`,
  `PartyRollback`, `RollbackPlay`, `PeerWire`/`PartyWire`/`NetTransport`
  merge into these.
- **Plugins.**
  - `PluginManifest.version`, plus `dependsOn` with version ranges.
  - `SimulationVersion.plugins: Map<String,int>`.
  - `WireHello` carries a `SimulationVersion`.
  - Event codecs: `EventRegistry.declare<T>(…, codec:)`.
  - The Wasm host accepts a range of ABIs.
  - A field declares its scale: Q16.16 holds ±32 768, which is not enough
    for double positions.
- **Agents and IDE.**
  - `dart_mcp` is wrapped in our own `ToolSpec`/`ToolResult`.
  - Tool annotations (read-only, destructive) and a `tools` permission
    checked in `McpTools.addTool`.
  - `outputSchema` wherever `structuredContent` is returned, and it goes
    into `.mcp`.
  - Snapshots for plugin tools.
  - `ext.flutter3d.version`, with types and result keys in `.vm`.
  - One tool naming scheme, `area.verb`, with the old names kept as
    aliases.
- **CLI (item 32).**
  - One `flutter3d` executable.
  - Subcommands, flags and exit codes are frozen (0, 1, 2 usage, 3
    refused/stale).
  - `--json` with its own schema version.
  - `plugins --check`.
- **Conformance.** The badge names its suite version (`conformant@1.0`).
  New checks go only into a new suite version.

## D. Formats

1. **One JSON envelope:**

   ```json
   {"format": "f3d.level", "version": N, "requires": [...], "generator": "..."}
   ```

   - A shared `FormatDocument` base keeps unknown keys.
   - Old shapes still read: `{"version":N}`, `{"f3dfx":N}`, `{"f3dplugin":N}`.
   - Unknown keys are lost today by `.f3drun`, the share bundle, the input
     tape, telemetry, snapshots and the racing track.
   - These are not versioned at all today: `flutter3d_assets.yaml`, the
     dock layout, `recent.json`, and the conformance and catalogue JSON.
   - `FrameCapture` returns null for a newer file. It must refuse with a
     reason instead.
2. **Stable ids in levels and prefabs.**
   - Entities, brushes and lights get an `id`.
   - Overrides are keyed by an id path. Today they use a name or `#index`,
     so renaming or reordering inside a prefab silently retargets them.
   - Properties move under `props` or `components.<ns>`, and the top level
     is reserved. Today `id`, `layer` or `rotation` added in 1.x could
     collide with users' properties.
   - This has to be settled in the first version of the prefab format
     (item 12).
3. **Growth in `.f3d`.**
   - A record's stride comes from the section (`length ~/ count`), so a
     record can grow at the end.
   - A flags word in the directory, with bit 0 meaning "must understand".
   - A vendor kind range (≥ 0x8000_0000).
   - A u64-offset variant reserved now.
4. **The units contract (item 29)** goes into `docs/CONTRACTS.md`: SI,
   Y up, right-handed, radians, linear colour except where marked sRGB.
   Formats and tool schemas refer to it, and imported assets carry a
   `units` header.

## E. Conventions (wave 4, item 28)

1. **American spelling in identifiers.** Today the API has colour 115
   times against color 373, centre 82 against center 15, and Behaviour 79
   times.
   - They mix even inside one class: `sunColor`/`sunColour`,
     `sceneColour`/`sceneColor`, `texelsPerMetre`/`texelsPerMeter`,
     `center`/`centre` in `DebugLines`.
   - Docs may stay British.
2. **Teardown is `dispose()`.** `close()` is only for connections and
   streams.
   - It returns `void`, or `Future<void>` when IO has to finish.
   - Today two verbs live on one object: `PointerLock`, `DesktopInput`,
     `AttachedRun`.
3. **Creation verbs.**
   - `create` is synchronous, for the GPU.
   - `open` is asynchronous, for a device or a session.
   - `load` is for an asset, `decode` for bytes, `parse` for text.
   - `make`, `take` and `get` go.
   - A device is opened through `open*` only.
4. **Units.**
   - Angles are in radians. The `Degrees`/`Deg` suffixes go (`halfAngleDegrees`, `sunElevationDeg`), and `fov` becomes `fovY`.
   - Time is `double` seconds in the simulation. `Duration` appears only at the Flutter boundary.
5. **Booleans.** Getters start with `is`/`has`/`can`/`uses`/`supports`.
   Settings fields stay bare (`enabled`). No positional `bool` parameters
   (37 today).
6. **Exceptions (item 21).**
   - A root `Flutter3dException` in `flutter3d_plugin_api`, the package
     with no dependencies.
   - Sealed families: format, capability, plugin, resource.
   - `*Error` only for `Error`; `*Refused` only for result variants.
   - Today there are about 65 types with no root, and six `*Error` that
     implement `Exception`. `UnsupportedCapability extends UnsupportedError`.
     `StaleShaderBundle` and `ShaderBundleRefused.stale` duplicate each
     other, and bare `FormatException` is thrown in readers.
   - Every thrown type appears in a snapshot.
     `ShaderBundleBuildException` does not today.
7. **Null is not an error.** 74 `create`/`open`/`load` members return
   null on failure today. They will throw or return a sealed result
   instead, and "null when absent" is stated in the docs.
8. **Ownership (item 20).**
   - Anything that holds GPU or native memory has `dispose()`: `DeviceMesh`,
     `RenderTexture`, pipelines, shaders, samplers.
   - Handles have private constructors (11 public ones with `Object
     backend` today).
   - Containers document whether they own or borrow, as `Material` does
     its nine textures.
   - Reference counting comes from `ResourceCache`.
9. **Events in two styles:**
   - `Stream` for external asynchronous sources;
   - `Registration on*(handler)` for engine events.
   - Listener objects only as plugin interfaces. There are eight styles
     today.
10. **Settings.**
    - `final` and `const`, with a complete `copyWith` that can also reset
      a field.
    - One suffix, `Settings`; `*Descriptor` only in the HAL.
    - Today `AiSettings` lacks 11 of its 12 `copyWith` fields, 35 settings
      classes have none, and there are seven suffixes.
11. **One colour type in the engine**, linear. Flutter `Color` only in
    widgets. Today there are five representations.
12. **No synchronous IO or readback on the main API.** `Storage` becomes
    asynchronous. `readBufferSync` moves into the testing library.
13. **Light in photometric units:** lux, candela, lumen. Today one unit
    is 1843.2 cd/m².
14. **Facades.**
    - `flutter3d` reaches the simulation, audio and physics entry points.
    - `flutter3d_game` re-exports `flutter3d`.
    - A first game takes two imports and no `hide`. Today it takes five
      imports and two `hide` clauses.

## F. Fewer packages (wave 4, item 16)

The game-layer review proposes going from 71 packages to about 25.

**Engine and runtime:**

- `flutter3d`: core, hardware, mesh, model_core, shaders, plugin_runtime
  and cpu.
- `flutter3d_plugin_api`, on its own version line (decision 2 in
  `1.0-stability.md`).
- `flutter3d_backends`: impeller, webgl and webgpu.
- `flutter3d_sim`: sim, physics, particles and voxel.
- `flutter3d_physics_native`, `flutter3d_effects` (plus wrecks), and
  `flutter3d_app`, the main facade with `Flutter3dView`.

**Game, audio and UI:**

- `flutter3d_post`: the six families plus standard.
- `flutter3d_audio` and `flutter3d_audio_soloud`.
- `flutter3d_game`: plus camera, reactions, soundtrack, ghost,
  seeded_levels, world and ragdoll.
- `flutter3d_game_ui`: hud, touch, access, screens, photo, capture and
  settings.
- `flutter3d_genres`: four libraries. This needs the hard dependency of
  shooter on physics_native removed first.

**Network, editor and agents:**

- `flutter3d_net` (plus party and cloud) and `flutter3d_net_webrtc`.
- `flutter3d_editor` and `flutter3d_mcp`.

**Flame, XR and education:**

- `flame_flutter3d` (plus audio), `flame_multiplayer` and
  `flame_multiplayer_dashwire`.
- `flutter3d_xr`, and `flutter3d_education` (lab, lti, chemlab, lessons).

**Platform, dev and unpublished:**

- Platform: `pad_input`, `pointer_lock`.
- Dev: testing (which absorbs conformance), build, lints.
- Unpublished: `flutter3d_samples`.

**Conditions:**

- Plugin discovery accepts several markers per package.
- `migrate` handles the renames and import moves.
- `audio` no longer depends on physics.
- `app` no longer depends on `editor_core`.

## G. What can wait until minor releases

These are all additive:

- texture streaming and GPU particles;
- RenderDoc on top of the debug groups;
- `.f3dmat` compute on the GPU;
- archetype storage in the ECS and a native Wasm runtime;
- chunked origin;
- `GameServices` (reserve the name now);
- MiniMap marker kinds;
- HRTF and an XR runtime behind the existing seams;
- a GitHub Action, SARIF, and third-party migration tables;
- template kinds from git;
- an asset-store manifest on the shared envelope;
- glTF export of levels;
- a leak tracker;
- a common `Issue` type, with the old six kept as subtypes.

## Decisions (Dmitrii, 2026-10-08)

1. **Packages: a middle path, about 40, not 25.**
   - These merge:
     - the 14 game addons become 3–4 packages: gameplay, UI, presentation;
     - the 6 post families plus standard become one `flutter3d_post`;
     - the MCP servers become `flutter3d_mcp`;
     - lab, lti and chemlab become `flutter3d_education`.
   - The core, the backends, sim, physics and the genres stay as separate
     packages.
   - §F is the long-term direction, not the 1.0 plan.
2. **New names for the colliding types.**
   - `Material` becomes `SurfaceMaterial`, and `Ray` becomes `WorldRay`.
   - The duplicates are renamed as well: `Pose`, `Body`, `FramePacing`,
     `ReadoutStyle`, `KeyKind`, `ChaseCamera`, `Heightfield`,
     `ParticleSystem` and `Selection`.
3. **World positions use our own type, `WorldPosition`.**
   - It is immutable, with `double x, y, z`.
   - It has explicit conversions to and from `Vector3` relative to an
     origin or the camera.
   - `vector_math` (float32) stays in local spaces, the view and GPU
     buffers.
   - `vector_math_64` is not brought in.
4. **Errors from create, open and load are exceptions** from the
   `Flutter3dException` hierarchy. `null` remains only for "absent", and
   the docs say so.
5. **Types that users implement are `abstract base class`** with
   defaults (§A.1). Mocks go through `extends`.
6. **Two event styles.**
   - `Stream` for external sources, `Registration on*(handler)` for engine
     events.
   - `RenderListener` and `ElementsListener` stay as plugin interfaces
     with `.toBus`.
   - Widgets keep Flutter's `onX` callbacks.
7. **Strings in widgets come from `Flutter3dGameLocalizations`**, in
   English and Russian out of the box, and a parameter can still override
   them. Library calls return message ids.
8. **Light is in photometric units in 1.0.** `migrate` converts the
   literals, so the picture does not change.
9. **Formats.**
   - One envelope with a `FormatRegistry`; the old shapes read as v1.
   - Unknown keys are kept.
   - Stable `id`s in levels and prefabs, overrides by id path, and
     properties under `props`.
   - All of this before rc.1.
10. **`dart_mcp` and `flutter_bloc` are wrapped.**
    - `ToolSpec` and `ToolResult` are our own types.
    - `SettingsCubit` becomes internal, and the API exposes a
      `ValueListenable`.
11. **Colour is our own `LinearColor`** (r, g, b, a in linear space, with
    `.fromSrgb` and `.fromColor`). Flutter `Color` appears only in
    widgets.
12. **Demo content goes into `flutter3d_samples`** with `publish_to:
    none`. The dungeon, strategy and the editor take it from there.

Everything else in §A–§E is taken as recommended.

## Null-as-error sites to convert

Wave 3, step 0 put the exception root in place (`Flutter3dException` and its
four families in `flutter3d_plugin_api`), so decision 4 can now be carried
out. The step did not convert anything; this is the list for the agents who
own each package.

How it was made: every member in the committed `.api` snapshots whose name
starts with a creation or reading verb (`create`, `open`, `load`, `decode`,
`parse`, `read`, `bake`, `find`, `get`, `take`, …) and whose return type is
nullable. That catches more than the 74 the review counted, because some of
these return null for "absent", which is allowed. The ones marked "absent"
look like that from their name and type; the owner decides. For each of the
rest, a failure throws a leaf of the right family, and the doc says what
null still means, if anything.

A second list belongs here too: readers that throw a bare `dart:core`
`FormatException` (§E.6). These should throw a package leaf of
`Flutter3dFormatException`. Counted with
`rg -c "throw (const )?FormatException\("` over each package's `lib/`:
`flutter3d_core` 66, `flutter3d_build` 46, `flutter3d_particles` 42,
`flutter3d_sim` 37, `flutter3d_plugin_runtime` 31, `flutter3d_model_core` 9,
`flutter3d_webgpu` 9, `flutter3d_plugin_api` 8, `flutter3d_voxel` 6,
`flutter3d_hardware` 5, `flutter3d_shaders` 3, `flutter3d_app` 2,
`flutter3d_game` 2, `flutter3d_game_strategy` 2, `flutter3d` 1,
`flutter3d_model_mcp` 1.

## Wave 3d decisions

Sealed or open, per type (§A.2). The test was whether exhaustive matching is
the point of the type: a protocol or a result the engine interprets stays
sealed, and a state set a genre may grow becomes a class with constants.

| Type | Package | Was | 1.0 | Why |
|---|---|---|---|---|
| `TimelineCommand` | flutter3d_game | sealed | sealed | What the timeline reports it did (paused, stepped, branched, scrubbed, swapped, replayed). A tool interprets the set exhaustively, so a new command waits for a major. |
| `RunStatus` | flutter3d_game | sealed | sealed | A result with fixed shapes (`RunLoading`, `RunPlaying`, `RunFailed`) that every screen switches over. |
| `ScrubAnswer` | flutter3d_game | sealed | sealed | A result (`ScrubMoved`, `ScrubRefused`), matched exhaustively by the scrub UI and the VM extension. |
| `CloudFetch` / `CloudPut` | flutter3d_game | sealed | sealed | The whole of what a fetch or a write can answer (a copy, none, or unreachable; kept, overtaken, or unreachable). A sync switches over them exhaustively, so an unhandled case would be a silently lost run. |
| `StrategyOrder` | flutter3d_game_strategy | sealed | sealed | Orders are written to the order tape, and the simulation executes each one. An order the simulation cannot execute is not an extension point, and a new order is a simulation version. |
| `ActionBinding` | flutter3d_game | sealed | sealed | `ActionInput` evaluates the five shapes exhaustively. A new device shape comes with the engine, in a major. |
| `GameState` | flutter3d_game_shooter | enum | class with constants | A genre state set that will grow (a level on a timer). No `paused`: pausing belongs to the loop (`EngineLoop`, `PauseGate`), and a paused run is still `playing`. `outcome` is the exhaustive answer. |
| `RunState` | flutter3d_game_platformer | enum | class with constants | Same reason as `GameState`. |
| `RacePhase` | flutter3d_game_racing | enum | class with constants | The losing phase for a race against the clock is already foreseen in its own doc. |

The three classes keep `values`, `name` and the constants. `outcome` becomes
a field, and `byName` reads a snapshot's word (null when unknown). A `switch`
needs a default case.

Other decisions made in the wave:

- **Demo content goes to `flutter3d_demo_content`, not `flutter3d_samples`.**
  Decision 12 named `flutter3d_samples`, but that package is already
  published, holding the Khronos fixtures (0.7.1 and 0.8.0 are on pub.dev),
  so it cannot become `publish_to: none`. The new package holds shooter's
  `sample.dart` (now `shooter_sample.dart`), `staging.dart` (now
  `shooter_staging.dart`, with the only `stage()`/`Staged`), `crypt.dart`,
  strategy's `map_world.dart`, and the repo hygiene checks (`soundTableIn`,
  `creditGaps` in `repo_checks.dart`). Published packages take it only as a
  dev dependency. Moving it out also drops shooter's and strategy's hard
  dependency on `flutter3d_physics_native`.
- **`TorchFire`, `LevelWalk`, `AutomapView`, `SoundOcclusion` and
  `openRegistryFor` stay in `flutter3d_game`.** By usage they are
  engine-generic:
  - `TorchFire` is the return type of the `FixtureAppearance` contract, used
    by two demos.
  - `LevelWalk` is the walking body used by the sandbox, the modeller's play
    mode and the game example.
  - `AutomapView` draws the simulation's `Automap`.
  - `SoundOcclusion` is a pure gain function over a `CollisionWorld`.
- **Two genres in one engine: shared or replaced kinds.**
  - `EntityKinds` shares a kind that is `==` to the one already held. For a
    `const` kind that is one object, so the format's `DoorKind` spoken by two
    genres is held once, until the last holder lets go.
  - A different kind under the same type is still refused, naming both
    owners.
  - `replace`/`replaceAll` (`GenrePlugin.replaceKinds`) put one over the
    other while held, and bring the old one back afterwards.
  - Namespacing by genre was rejected: a level's `key` is the format's word,
    and `LevelScope` reads it.
- **`GenrePlugin<S>` lives in `flutter3d_sim`**, the one package all four
  genres share.
  - The step stays one EngineLoop system per genre, `<genre>.step`, under the
    base getter `systemName` (each genre keeps `static const stepSystem`).
  - The order inside a step is what a tape replays, so controllers are not
    split into separate loop systems. Instead each genre with a simulation
    exposes named `StepSystems` moments inside its step:
    - `ShooterPhases` (existing);
    - `PlatformerPhases.afterRunner`;
    - `RacingPhases.afterVehicles`.
  - `StepSystems` is not deprecated (the sim review's note covers
    `GameLoop`/`FixedStep`, not `StepSystems`).
- **Genre cameras keep their presets and take `reframe:`**, a function from
  the preset framing to the `CameraFraming` the `VirtualCamera` shoots. A
  replacement can wrap the preset and keep the subject and look the camera
  feeds it. `FlameChaseCamera` (renamed from flame's `ChaseCamera`) is
  untouched otherwise.
- **`StepClock` stays an `abstract interface class`.** Its implementers are
  Flame `Component`s, and `HasFixedStep` is a mixin on `FlameGame`; games
  subclass both. `base` would force every such game class to be
  `base`/`final`, and an `abstract base mixin class` cannot be mixed into
  `Component` subclasses that games extend freely. It does not grow: a
  capability arrives beside it, as its doc says.
- **`MixingBackend` and `DirectionalBackend` stay interfaces** but no longer
  extend `AudioBackend` (now an `abstract base class`). They are
  capabilities a backend opts into: `extends AudioBackend implements
  MixingBackend`.
