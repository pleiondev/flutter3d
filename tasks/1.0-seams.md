# Seams for after 1.0.0 (2026-10-10)

Decided with Dmitrii on 2026-10-10. Strict semver from 1.0.0
(`1.0-stability.md`) means a feature planned for 1.x has to arrive as an
addition. Most of the tree already allows that: `base` classes take new
members with defaults, registries take new entries, formats migrate. This
plan lists the seams the 1.0 contract still lacks for the directions we
expect after it, and the order those directions come in. It does not repeat
`1.0-rc1-plan.md`: decals, multi-view, the LOD and culling hooks, compute
steps, the pacing proofs and rollback on phones are there already.

## What a minor cannot fix

A 1.x minor can add almost anything. It cannot:

1. change the shape of a public type an application touches;
2. add a required member to an interface implemented outside the repo;
3. change the default simulation, because tapes and matches depend on it;
4. change what a field in a format means;
5. **add a value to a public `enum` or a subtype to a public `sealed`
   class**, because that breaks every exhaustive `switch` in user code.

So 1.0 has to freeze seams, not features. Item 5 and the policy that
follows from it are in `1.0-stability.md` since step 2S.

## Seams in the contract (rc.1; rc.2 at the latest)

**S0. Growing enumerations.** Every public `enum` and `sealed` type that
may gain a member (light types, quality tiers, `ComputePlacement`, phases
of matter, refusal reasons) becomes a class with static constants, as
`DeviceFeature._` already is, or is documented as closed for good. A
structure rule reads `api/*.api` and fails on a public `enum` or `sealed`
type that is in neither list.

**S1. `MaterialState` per body.** `PhysicalMaterial` is `final` and
`const`, and stays so: it is the reference. What a body is like right now
is separate state:

- an ECS component with an open set of quantities, each keyed by a
  namespaced id (`f3d.wetness`, `<pluginId>.charring`) and holding a
  `Quantity` from `flutter3d_foundation`, so the unit travels with it;
- unknown quantities are kept through saves, snapshots and the wire, as
  unknown fields are kept in formats;
- `PropertyLaw.at(MaterialState)` (3A) reads it, and the `bindings:`
  section (rc.2) binds a quantity to a render material's parameter.

Living materials in 1.2 then touch no existing type.

**S2. A contact event on the bus.** `Contact` exists; no `GameEvent` for
contacts was found in `flutter3d_physics` or `flutter3d_sim`. One `final`
event carries both bodies, the material **ids** (not the materials), the
point, the normal, the impulse, the relative velocity and the phase
(begin, persist, end), in a deterministic order so tapes replay it.
Physics-driven audio, impact decals, damage and destruction are written on
it. Its fields have to be right the first time, which is why it lands
before the freeze.

**S3. Fields.** One contract for a 3D grid of quantities shared by the
simulation, the renderer and audio: a transform, a unit (`Quantity`), CPU
or GPU residence, the frame-graph step that writes it and the steps that
read it, `DeviceFeature.texture3D` with a typed refusal where it is
missing. Volumetrics, the environment, granular media and weather stand on
it. It lives in an interface package with its own version, as
`flutter3d_plugin_api` and `flutter3d_hardware` do, because it will grow
faster than the engine.

**S4. A subsystem declares what it reads and writes.** A solver registers
as a subsystem with the quantities and fields it reads and writes and its
place in the step. `SimulationVersion` is composed from the versions of the
enabled subsystems. Two things follow:

- a new solver in a minor is switched on through `SimulationProfile` and
  leaves the default simulation, its tapes and its matches alone;
- a later simulation-graph checker validates declarations that already
  exist instead of reshaping the API.

**S5. Asset identity.** `AssetSource` is already `abstract base` and
sendable. Before the freeze it gains:

- optional `contentHash` and `version`, null by default; the contract of
  `key` says the version is part of it;
- the licence and the author on the result of a model load.

**S6. A channel for research.** There is no `@experimental` in 1.x. Work
that is not ready lives in separate `0.x` packages (`flutter3d_lab_*`)
that depend only on stable seams. A structure rule: no 1.x package depends
on a 0.x package. A lab package that proves itself moves into 1.x in a
minor.

**Acceptance.** A sample plugin outside the repo, built against the public
API only, adds a quantity to `MaterialState`, listens to the contact
event, writes a field and registers a subsystem; the conformance suite
passes it on four backends. The S0 rule is green.

## The model hub ships in 1.0.0

models.pleion.dev is part of the launch: the cookbook and the site's
examples load models by reference, with nothing to download. That makes the
hub part of the frozen contract.

**rc.1, the contract:**

- S5 in full.
- The reference format, fixed for good: `<uuid>@<n>`, optionally with a
  `sha256` to check. References will live in other people's code for
  years.
- The client types: a sendable `HubAssetSource`, `HubRefused` with its
  reasons (`notFound`, `withdrawn`, `hashMismatch`, `offline`, `tooLarge`,
  `protocol`) as a class with constants under S0, and the cache policy.
- The server protocol is an interface, like MCP and the network hello.
  Requests carry the protocol version; the server announces its own; a
  different major is refused with a sentence; within a major the protocol
  only grows. The response schema is snapshotted in CI, as `api/*.mcp` is.

**rc.2, the implementation (additive):**

- `flutter3d_hub`: plain Dart, its own package, so the engine core has no
  network dependency; `flutter3d` re-exports it with a `show` list.
- Hash check after download, an on-device cache keyed by hash, offline
  reads from the cache.
- `doctor vendor <ref>` copies a model into `assets/` and rewrites the
  reference to a `BundleAssetSource`.
- The cookbook and the site's examples move to hub references; that is the
  test.

**The server, before the 1.0.0 tag:**

- Versions are immutable. A public model cannot be deleted, only hidden
  from the catalogue.
- A mirror of public models (GitHub Releases or a public bucket); the
  client falls back to it when the main server does not answer, and the
  mirror's address is in the 1.0 client.
- `Cache-Control: immutable`, CORS for the web, a rate limit on uncached
  requests.
- A quota, sign-in to upload, a report button, terms of use and a DMCA
  procedure, a licence field on publishing.
- One sentence in SUPPORT: hub references are for examples and prototypes;
  an app in production vendors its models.

**Acceptance:**

- the cookbook builds and renders from the hub, and with the network off
  from a warm cache;
- a tampered file is refused with `hashMismatch`;
- with the main server down, an example loads from the mirror;
- a 1.0 client works against the next minor of the server.

**Risk.** The hub adds a service with its own schedule to rc.2, and rc.2
comes before 1.0.0 without exception. The server checklist above is a
condition of the tag, next to P1–P5: the client types frozen in rc.1 stay
in the contract either way, and a 1.0.0 with the hub "coming soon" is
worse than one without it.

## After 1.0.0, by minor

| Release | What | Seam | Proof |
|---|---|---|---|
| 1.1 | The cookbook grown, first-scene time, adoption work | S5, hub | Time to a first scene; projects using flutter3d that we did not write |
| 1.2 | Living materials: wetting and heat change PBR and mass. Physics-driven audio (modal synthesis) as an **outside** package | S1, S2, `bindings:` | A video; the audio package needs no change to the engine |
| 1.3 | Volumetrics fed by simulation fields; a heat, steam and light laboratory in `flutter3d_education` | S3, S4, 2K | Mass and energy balance in a test; the frame in budget on the A55 |
| 1.4+ | Probe GI, a streaming scheduler, character animation: when users ask | The 2.2 hooks | A request |

Every minor passes: an API diff of additions only; the default
`SimulationVersion` unchanged; goldens unchanged, or the old look behind a
settings flag; conformance on four backends; the outside sample plugin
builds.

## Research in 0.x packages, no dates

Granular media (MPM), thermo-fluid-structure coupling, reaction kinetics,
inverse physics, uncertainty, the simulation-graph checker (on the S4
declarations), Gaussian-splat hybrids. A spectral reference renderer is an
offline tool for checking the runtime, not a runtime feature. Virtualized
geometry waits until flutter_gpu has compute and indirect draws.

Not without a customer: an industrial digital-twin data contract and
neural physics.

## Order of work

1. S0: list the public `enum` and `sealed` types from `api/*.api`, decide
   each, write the rule.
2. S5 and the hub's rc.1 contract (reference format, client types,
   protocol version and schema snapshot).
3. S2, then S1 beside 3A.
4. S3 and S4, then the outside sample plugin and its conformance run.
5. S6's rule.
6. rc.2: `flutter3d_hub`, `vendor`, the cookbook on references; the server
   checklist before the 1.0.0 tag.
