# The plan for 1.0.0-rc.1 (2026-10-09)

This is the execution order that comes out of `1.0-readiness-review.md`:
its findings (§2), its target state (§3), its first work list (§4) and the
twenty decisions of the same day (§6). It replaces §4 of the review as the
list to work from; the review stays as the evidence.

The engine is for games, digital twins and virtual laboratories. The
candidate carries the whole 1.0 contract: the API shape, the materials
catalog in full, the hot-path work, the demos without crutches, and no
`@Deprecated` at all.

## Two candidates (decided 2026-10-09, night)

Two readers of the public surface, a Flutter developer new to 3D and a
senior engine programmer, agreed on one thing: reliability and
measurements first, breadth after. So the candidate splits in two.

- **`1.0.0-rc.1` is reliability and the shape of the API**: waves 0, 1,
  2 (with step 2.2, because the extension points are shape), 3 (with
  steps 3.0 and 3.1), step 4.1 (the hot path, the shader selection, the
  boundaries) and wave 5, plus the proof on hardware below. Everything a
  user could write against rc.1 is the 1.0 contract.
- **`1.0.0-rc.2` is breadth**: step 4.2 (the demos and the examples on the
  new entry points), wave 4.5 (the viewer widget, text and sprites, video,
  reverb, the viewer kit, point clouds, the three lighting models,
  assessment and rules, terrain and grass, WebXR), the editor in the plugin
  contract (D32), the Wasm render ABI (D29) and the pipeline document's
  editor side. Each of these is additive under the rc.1 contract.
- **rc.2 is mandatory; 1.0.0 follows rc.2, never rc.1** (decision 59 of
  the product review). The types rc.1 lands as contracts with no
  implementation behind them (`XrSession` base, the `Rule` and
  `f3d.experiment` format ids, the `bindings:` section, `f3d.pipeline`,
  the Wasm render ABI, `PropertyLaw`) are filled by rc.2 before anything
  freezes, so no empty type reaches 1.0.0.
- **Between the candidates a break is allowed; at 1.0.0 the contract
  freezes.**

**Proof on hardware is a condition of the rc.1 tag** (decision 51):

Each proof has a threshold (decision 60 of the product review); a report
without its number is not a proof. The numbers live here and in
`tool/pacing.sh` as `--fail-on`.

1. **P1** A pacing report on a Galaxy A55 and a named mid-range iPhone
   (iPhone 13 or SE 3rd generation) for three demos (platformer, racing,
   dungeon), release build, native resolution, three runs of two minutes
   after sixty seconds of warm-up, committed under `doc/pacing/` with the
   device, the build and the commit. Threshold: p50 ≤ 16.7 ms, p99 ≤
   33.3 ms, frames over 50 ms ≤ 0.1 %, none over 100 ms after warm-up,
   resident memory at the end ≤ 1.10 × the value at 30 s and ≤ 400 MB on
   the A55, ≤ 300 MB on the iPhone. `pacing.sh` gains the RSS column
   (`adb shell dumpsys meminfo` once a second).
2. **P2** A two-hour soak on the A55, inline and in the isolate, the
   platformer on a looped tape, the RSS graph committed. Threshold:
   RSS(120 min) ≤ 1.15 × RSS(10 min); no frame over 250 ms; no crash or
   ANR; GC pauses over 50 ms at most one a minute. Needs `tool/soak.sh`,
   which does not exist; **if it is not written before rc.1, P2 is an
   rc.2 condition.**
3. **P3** A parity table for the C core on the racing and shooter tapes
   over 1 000 steps, in `doc/parity/c-core.md`, as §9.3 of ARCHITECTURE
   has for the Dart maths. Threshold: the world digest every 100 steps
   bitwise equal on clang/ARM64 Android (the A55), clang/ARM64 iOS,
   clang/x64 Linux, MSVC/x64, dart2js and dart2wasm. On a mismatch,
   `-ffp-contract=off` on every target and a retry; if it still differs,
   `WireHello` gains an architecture field, a match across architectures
   is refused with a sentence, and SUPPORT says "rollback within one
   build target". `digest_platforms.sh` grows to tapes and wasm.
4. **P4** Rollback between eight phones over real Wi-Fi (RTT measured and
   written), ten minutes at 60 Hz, `inputDelay 2`, `maxRollbackFrames 8`.
   Threshold: `droppedCorrections` ≤ 0.5 % of steps; p99 resimulation
   time per step ≤ 8 ms on the A55; all eight world digests equal at the
   last step; no session dropped. Needs a resimulation timer in
   `RollbackSession` (today only `isResimulating`); **if the timer or the
   phones are not there before rc.1, P4 is an rc.2 condition.**
5. **P5** The APK, IPA and web sizes of `flutter3d_app/example` after the
   shader selection, written into the quickstart with the date and the
   commit. Threshold: APK arm64 release ≤ 20 MB, IPA ≤ 25 MB, web
   (`main.dart.js`, shaders and the C core's wasm, gzip) ≤ 5 MB, and the
   shader part at most half of today's.
6. **Nightly** The A55 on the `impeller` runner runs the three demos
   nightly with p99 ≤ 33.3 ms as the red line; **seven green nights in a
   row before the tag**; a "stale" badge after 48 hours without a run.

## How the waves work

- **One checkout, many agents.** Agents share the working tree, so within a
  wave each agent owns a set of packages and edits nothing outside it. Where
  two agents must touch one package, the file lists are written out.
- **Shared files are integration's.** Only the integration step of a wave
  touches `api/*.api`, `api/*.mcp|vm|cli`, `lib/fix_data.yaml`,
  `packages/flutter3d_build/lib/migrations/0.8_to_1.0.yaml`, the root
  `pubspec.yaml`, `tool/structure/*`, README, ARCHITECTURE, CONTRACTS,
  SUPPORT and the site. An agent that needs a migration entry or a rule
  writes it into its hand-back, and integration applies it.
- **A wave ends green.** Integration regenerates the snapshots and
  migrations, runs `flutter analyze`, `dart run tool/structure.dart` and the
  suites of every package the wave touched, then commits by area and
  pushes (decision 19). The next wave starts from a pushed tree.
- **Every break comes with its migration** (CONTRIBUTING), so each wave's
  integration runs `dart run api_snapshot:migration_seed` in `tool/api` and
  `dart run tool/generate_migrations.dart --check` in `flutter3d_build`.
  `1.0-api-migrations.md` gives each break of waves 2 and 3 its migration
  kind, adds wave M (the migration tools, before wave 2) and step 2.0, and
  holds each format to one version bump per candidate. From wave 2 on,
  integration also runs the wider corpus (`tool/migrate_corpus.sh`) and
  `migrate --data` over the fixture project. Its section "What 1.x will
  need from the frozen contract" adds fields and signatures to rows 1A, 2B,
  2D, 2E, 2F, 2X, 3E0, 3A, 3F and 4E and to step 2.0; each owner reads it
  with its row.
- **Tests are written by breaking the code** (CONTRIBUTING). A fix without a
  red test first is not done.
- **A wave ends reconciled.** Before the commit, integration checks the
  documents and the plans against what the wave actually did:
  - **Documents.** README, ARCHITECTURE, CONTRACTS, SUPPORT, CONTRIBUTING,
    the site pages and the package READMEs and CHANGELOGs say what the code
    now does: the new types, the changed behaviour, the counts.
  - **Plans.** Each item of the wave's rows in this plan and in
    `1.0-api-migrations.md` gets a status line (done, partial with what is
    left, moved and to where). Findings that change a later wave are written
    into that wave's row. A decision taken during the wave is written where
    the plan states the old one, marked as amended.
  - **Hand-offs.** What a wave hands to later ones (re-recordings, goldens,
    proofs on hardware) is listed under the wave it lands in.
  - **The dashboard.** Each row's and each goal's status goes into
    `tasks/1.0-progress.json`, and `tool/progress.sh` rebuilds and publishes
    the progress page from it, the plans and the tree.

Sizes: **S** a day for an agent, **M** two or three, **L** a week. They are
for ordering, not for promising.
