How the release candidate works:

- **Constraints.** `^1.0.0` does not admit `1.0.0-rc.1`, because a
  pre-release sorts below its release. So every package asks its siblings
  for `^1.0.0-rc.1`. That constraint also admits the final `1.0.0`, so it
  stays as it is when 1.0.0 ships.
- **CHANGELOGs.** The top heading is `## 1.0.0-rc.1`. The final release
  adds a `## 1.0.0` section above it, listing only what changed since the
  candidate.
- **What users see.** pub.dev keeps 0.8.x as the default version. The
  candidate is opt-in, with `^1.0.0-rc.1`, and the quickstart says so.
- **Mistakes.** A published version cannot be deleted. It can be retracted
  within 7 days, and plan B below is what to do instead on the day.

## The script

`tool/publish_layers.sh` reads the list above out of ARCHITECTURE.md,
uploads one layer, and asks `https://pub.dev/api/packages/<p>` every 20
seconds until each package of the layer lists its new version before it
starts the next layer. It reads the version list, not `latest`, which
stays on 0.8.x while the candidate is a pre-release.

```
tool/publish_layers.sh                      # dry run of every layer
tool/publish_layers.sh --check              # and `pub publish --dry-run` of each
tool/publish_layers.sh --layer L3           # one layer, still a dry run
tool/publish_layers.sh --publish --from 0   # the real upload
```

- **A dry run unless `--publish` is given.** It prints each package, its
  version here, whether pub.dev already has it, and the command it would
  run.
- **It carries on where it stopped.** A package whose version pub.dev
  already lists is skipped, so after a fix the same command (or `--from`
  the layer that failed) picks up the rest.
- **It stops at the first failed upload**, before the next layer, and
  prints plan B. A layer that is not listed within 20 minutes stops it too
  (`PUBLISH_WAIT_SECONDS` changes that).
- It needs `flutter pub login` first. It does not tag, push or deploy.

## Plan B: when a package goes up broken

pub.dev does not let a version be replaced or deleted, so the fix is a new
version, and the sheet decides which one in advance:

1. **The upload failed** (validation, a network error, a missing
   dependency on pub.dev). Nothing is published for that package. Fix it,
   commit, and run `tool/publish_layers.sh --publish --from <layer>`. The
   packages already up are skipped.
2. **The upload succeeded and the package is broken** (it does not
   resolve, pana fails it, an import is missing from a file list). Publish
   the same version with build metadata, `1.0.0-rc.1+1`, with the fix and a
   CHANGELOG line under `## 1.0.0-rc.1+1`. Pub sorts `+1` above the plain
   version, every sibling's `^1.0.0-rc.1` admits it, and no other package
   has to move. A second fix is `+2`. After 1.0.0 the same fix can be a
   patch of that package alone (`1.0.1` beside the rest at `1.0.0`): the
   shelf shares a major.minor, not a full version.
3. **The next layer is already up and depends on the broken part.** Do the
   same `+1` for the broken package; the dependents resolve to it on their
   next `pub get` and need no new upload of their own unless they were
   broken too.
4. **Retract** (the admin page, within 7 days) only a version that does
   harm when it resolves, such as one that deletes files or writes to the
   wrong place. A retracted version stays installable for anyone who has it
   in a lock file, so a retraction is not a fix; it only stops new
   resolves. `+1` comes first either way.

A `+1` is a fix, never an API change: if the fix needs a new or changed
public member, it is `1.0.0-rc.2` for that package instead, and the "a
break is labelled and versioned" rule holds it like any other release.
