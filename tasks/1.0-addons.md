# Addons (1.0)

Decided with Dmitrii on 2026-10-08.

- Post-processing and the reusable parts of games move out of the kernel
  and the demos into addon packages: `packages/addons/flutter3d_addon_*`.
- Each addon is an ordinary plugin on `flutter3d_plugin_api` (see
  `0.9-plugins.md`). So addons are the first examples for the community,
  and they are listed in the catalogue.
- What decides whether something becomes an addon is **whether another
  game would use it**, not whether it is already copied.
- This happens in 1.0, right after the plugin kernel and the render
  anchors (steps 1–3 of `0.9-plugins.md`) and before the 1.0 API snapshots.
  Moving it after 1.0 would be a breaking change.

## Post-processing: six families

Each family is one package. Each effect inside it is its own plugin, its
own `RenderStep` and its own switch, and it hangs on the engine's
anchors. The `standard` preset installs the families today's frame uses,
so goldens do not move.

| Package | Inside |
|---|---|
| `flutter3d_addon_light` | bloom, auto and local exposure, lens flare, vignette, grain, colour grade |
| `flutter3d_addon_shading` | SSAO, contact shadows |
| `flutter3d_addon_reflections` | screen-space reflections, planar reflections, reflection probes |
| `flutter3d_addon_atmosphere` | fog (with height fog, from the crypt's), volumetric fog, light shafts, the physical sky |
| `flutter3d_addon_motion` | depth of field, motion blur, temporal anti-aliasing |
| `flutter3d_addon_style` | outlines, toon, high contrast, viewport shading |

The kernel keeps the scene, the composite, tone mapping (the end of the
frame), the shadows and the edge-smoothing that every frame needs. It
also keeps the anchors around all of them.

### Progress (2026-10-08)

*The six families and the preset exist. Their tests are written and have
not run yet.*

- **The mechanism: an addon is the switch of a step the kernel draws.**
  `RendererSteps.provide(step)` (`flutter3d_core`, `renderer_steps.dart`)
  takes a step as a plugin's own. When the plugin is switched off, the step
  is *withdrawn*: `render`, `planFrame` and `renderPost` draw
  `settings.without(withdrawn)`, and `FrameResult.skipped` says so. A step
  nobody provides is drawn as its settings say. So in 1.0 the renderer
  without the preset keeps today's defaults, and with it, too: no
  user-visible change. While nothing is withdrawn the settings object goes
  through untouched. `RenderStepAddon` (`render_step_addon.dart`) is the
  plugin class every effect extends: an id, the steps it provides, the steps
  of its own it adds, a view manifest on plugin API 1.0. It registers
  nothing on an engine with no renderer.
- **Twenty-two plugins in `packages/addons/`**, each with its own pubspec
  marker for discovery:
  - light: bloom, lens flare (depends on bloom), auto exposure, local
    exposure, colour grade, lens distortion, vignette and grain. Lens
    distortion is not in the table above. It sits inside the composite with
    the film and the grade, so it went with them rather than stay as the
    only lens step in the kernel.
  - shading: ambient occlusion, contact shadows.
  - reflections: screen-space, planar, probes.
  - atmosphere: fog (height fog is `FogSettings.heightFalloff`, already in
    the kernel's fog), volumetric fog, light shafts, and the sky as a new
    added step, `skyStep`, switched by `SkySettings.enabled`.
  - motion: depth of field, motion blur, temporal anti-aliasing.
  - style: high contrast, viewport shading, and the outlines as a new added
    step, `outlinesStep`: `HighContrastSettings.outlineWidth`, needing high
    contrast; the plugin depends on the look's.
- **The preset is its own package, `flutter3d_addons_standard`**, rather
  than part of `flutter3d`. The umbrella would otherwise depend on six
  packages that depend on its own core, and an application that wants the
  switches asks for them by name. It is `standardAddons`, all twenty-two,
  and it exports the six libraries. It has no discovery marker: the
  families' own markers find the plugins, and a second one would name each
  twice. The broader `standard` preset of `0.9-plugins.md` (loop, elements,
  genres) can include it.
- **Proof that the frame did not move.** The capture that wrote
  `flutter3d_cpu/test/goldens/frame_order.jsonl` was run twice after the
  change: on a bare renderer, and with `standardAddons` installed through a
  `PluginManager` before the first plan. Both outputs are byte for byte the
  fixture (244 frames). With all twenty-two switched off, the "everything"
  frame keeps only the kernel: shadows and their moments, the irradiance
  update, render textures, the scene, decals, the transparent half, the
  depth pyramid, the composite, the upscale and the edge smoothing.
- **Tests to run** (written, not run): `test/*_addon_test.dart` in each
  family and `flutter3d_addons_standard/test/standard_addons_test.dart`
  (30 in all, each with a mutation named), then
  `flutter3d_cpu/test/render_anchors_test.dart` and
  `flutter3d_cpu/test/render_steps_test.dart` for the kernel's side.

### What stayed in the kernel, and why

**The settings types.** `BloomSettings`, `FogSettings` and the rest are
exported from each family's library, so one import reaches the plugin and
its settings, but they are still defined in `flutter3d_core`.
`RenderSettings` holds a field of each, and every addon depends on the
kernel for `RendererSteps`. Defining them in the addon would make the
kernel depend on its addons, a cycle the publishing order cannot lay out.
So core keeps the definitions and the old imports compile unchanged, which
is the "no API break" requirement from the other side.

*Done in 1.0 (scope addition 1):* `RenderSettings` carries settings in typed
slots. A `SettingsSlot<T>` is an id, defaults and an optional JSON codec;
`settings.extension(slot)` and `settings.withExtension(slot, value)` read
and write it, and the values of slots that are not fields live in
`RenderSettings.extensions`, compared by value and written by id. A
third-party addon defines its settings class and slot in its own package,
names the slot in `RenderStepAddon.settings`, and reads it from its steps;
nothing in the kernel changes. The built-in types are slots as well
(`SettingsSlot.bloom` and the rest), read and written through their fields,
and each family's addons add theirs. Their *classes* stay here for the
cycle above: the passes still read them as fields. They move when the pass
code does, and the slot is then the only way in. Keyed by id, not by
`Type`, because a runtime type is minified on the web and a level's
`renderSettings` section has to be read by another build.

**The pass code, every one of them.** Each pass is a private node in
`renderer_frame_nodes.dart`, a `part` of `renderer.dart`. Its `execute`
calls a private extension on `Renderer` (`_renderBloom`,
`_encodeViewportShade` and so on) that reads the renderer's pipelines,
pooled targets and uniform blocks. Moving one means making those public
first. Per family:

- *light*: bloom's chain and the flare use the renderer's mip chain and
  pooled targets. The meter's adapter state lives on the renderer between
  frames. The grade, the lens distortion and the film are arithmetic in
  the composite's shader and uniform block, shared with tone mapping, so
  they cannot leave without splitting the composite. **Follow-up:** a
  public composite uniform builder and a pooled-target API on `NodeFrame`.
- *shading*: SSAO, its blur and the contact shadows read the surface
  buffer, the half-resolution targets and the blue-noise table, and the
  lit passes read what they write through the renderer's bindings.
  **Follow-up:** public scene-input bindings (`FrameResourceIds` already
  names the resources, but not the binding the lit stages sample them by).
- *reflections*: the probes and planar captures re-draw the scene through
  the renderer's own scene encoder, and the scene samples them through its
  bindings; SSR reads the history ring. **Follow-up:** `encodeScene` as the
  public way a capture draws (it is public on `RenderServices` for
  contributors already), and probe and planar bindings opened.
- *atmosphere*: fog and the sky are compiled into the lit stages and the sky
  triangle of the scene pass, so they cannot move apart from it. The
  volumetric fog and shafts read the cascades and the light buffer.
  **Follow-up:** a material-language hook for the lit stages' air term, and
  public shadow and light bindings.
- *motion*: the velocity passes belong to no step. The resolve keeps the
  renderer's history ring and the jitter the scene pass draws with.
  **Follow-up:** history and jitter as public frame resources.
- *style*: the outline mask draws through the renderer's velocity stages;
  the high-contrast and viewport looks read its surface buffer and pooled
  targets. **Toon is an addon now, its stages are not** (scope addition
  10): lighting models are an open registry, `LightingModels`, and a
  `LightingModelAddon` registers models and hands the renderer their
  stages. `flutter3d_addon_style` defines `toonLighting` and registers it
  with `ToonLightingAddon`. `LightingModel.toon` is the same constant and
  stays in `LightingModel.builtIn` for 1.x, because the `Toon` stages are
  still compiled into every engine bundle and the CPU rasteriser, and a
  document naming `Toon` has to draw without the addon. **Follow-up
  (2.0):** the stages leave the engine bundle for a bundle the addon ships,
  and `toon` leaves `builtIn`.

When a pass does move, it becomes an `addNode` at the anchor it stands at
today, under the step its addon provides. The anchors were placed for
exactly that, and `frame_order.jsonl` will say whether it moved anything.

**Kernel steps with no addon:** shadows, caustics, irradiance update,
render textures, decals, hi-z occlusion, tone mapping, spatial upscale,
edge smoothing, sharpening.

## Reusable game parts

### Camera and frame

- **`flutter3d_addon_photo_mode`.** It is in the dungeon, the platformer,
  racing and the sandbox, and becomes one, with the physical camera from
  B6.22 of `0.10-plan.md` when that lands.
- **`flutter3d_addon_capture`.** Recording and sharing clips and runs:
  the platformer's `share_strip` and the reel tool kept from 0.9.
- **`flutter3d_addon_screens`:**
  - the title card;
  - the credits, read from the assets' `LICENSES.md`;
  - the ending and scoreboard;
  - the cutscene overlay (fade, subtitles, the way out);
  - the lens, which chooses the FOV by aspect, from the platformer.

### Reactions and sound

- **`flutter3d_addon_reactions`.** Shake, haptics and flashes as
  reactions to events on the bus's frame channel. Today this is
  `reactions.dart` in three games.
- **`flutter3d_addon_soundtrack`.** A cue sheet keyed by events:
  `soundtrack.dart`, `sounds.dart`, and the elements' sounds
  (`element_sounds.dart`), heard from the elements' events.

### HUD and access

- **`flutter3d_addon_hud`.** HUD pieces, readouts, the minimap (from
  racing), hints for a moment of play (`first_shot_hint` as a general
  rule), and an objective beacon (`way_out_glow`).
- **`flutter3d_addon_touch`.** Touch controls: the steering band, the
  pedal, the runner's and the crypt's sticks and buttons, as one set of
  widgets on the input layer.
- **`flutter3d_addon_access`.** High-contrast rings, colour-vision
  modes, and events spoken to screen readers (B6.23).
- **`flutter3d_addon_stereo_hud`.** The HUD panel for stereo, from
  racing.

### World and ghosts

- **`flutter3d_addon_ghost`.** A rival or a past run drawn from a
  replay's pose record: the platformer's `ghost.dart` and racing's
  `ghost_car.dart`. It goes with the 1.0 replay promise
  (`1.0-stability.md` §9).
- **`flutter3d_addon_daylight`.** The sandbox's day and night, on the
  physical sky.
- **`flutter3d_addon_ragdoll`.** A body that turns into a ragdoll when
  it dies, from the dungeon.
- **`flutter3d_addon_wrecks`.** Wrecks that burn and sink, with an oil
  slick, from River, on the elements.
- **`flutter3d_addon_horizon`.** The world past the simulated part, out
  to the horizon: Reef's floor and sea going on. The fifth genre uses it.
- **`flutter3d_addon_seeded_levels`.** Levels made from a seed when they
  are reached, from the dungeon's depths.
- **`flutter3d_addon_party`.** Local and network party sessions: racing's
  `party_race_session` and `net_race_session`, with the 1.0 network
  hello.
- **The ground function** (`terrain.dart` in Hollow and Reef) belongs to
  the fifth genre (`0.10-explore-genre.md`) and is not duplicated here.

### Progress (2026-10-08)

*Fourteen packages exist and the demos are on them. Their tests are
written and have not run yet. `flutter analyze` is clean and the structure
rules about them hold.*

**Two merges, to keep the package count sane.**

- The stereo HUD panel is `StereoHudPanel` in `flutter3d_addon_hud`. It is
  one widget, and a package of its own would have been a pubspec around
  thirty lines.
- Daylight and the horizon are one package, `flutter3d_addon_world`: the
  world around the simulated part, the sky over it and the ground past it.
  Each was one class.

So the list above is fourteen packages, not sixteen.

**Libraries, and three plugins.** Most parts are widgets and classes a game
composes. Reactions (`ReactionsPlugin`), the soundtrack (`SoundtrackPlugin`)
and access (`SpokenEvents`) are also view plugins on the bus's frame
channel. None carries a `flutter3d: plugin:` marker: each needs the game's
own table, and discovery builds a plugin with no arguments. None of the
fourteen depends on a genre, and none names one in code.

**A bug fixed on the way.** Racing's party sessions asked the relay with no
simulation version, so two builds of different simulations could be seated
together. `PartySession.open` requires the `SimulationVersion` and asks both
`joinParty` and `findParty` with it, and racing passes its own.

**What stayed in the demos, and why.**

- *Each game's tables*: which event shakes or flashes what, the cue lists
  and sound banks, what is spoken, the depth rules. They are the game, and
  the platformer's and racing's reactions read the simulation's state, not
  only events.
- *The demos do not install `ReactionsPlugin` or `SoundtrackPlugin` yet.*
  They decide per step from drained events, and moving to the frame channel
  changes the moment a reaction fires, which this pass promised not to
  change. The dungeon does install `SpokenEvents`, which only announces.
- *The credits lists are still data in each game.* Reading `LICENSES.md` at
  run time would need it bundled (most live in `assets_src/`), and the
  names on the screen differ from the headings. `CreditLedger.disagreementsWith`
  holds the list to the record in each game's test instead.
- *Words the genre rule keeps out of packages*: the controls lines, tallies
  (kills, laps, coins) and play-again sentences stay in thin adapters
  (`TitleCard`, `CryptEnding`, `SeasonEnding`). Racing's `pitStop` is
  `TouchDrive.corner`.
- *Game-specific halves*: `touch_runner.dart` (already four lines over
  `flutter3d_game`'s `TouchControls`), racing's `CarVoice` and its
  elements' wash, `party_race.dart`/`net_race.dart` (the rollback that
  drives the cars), saving a run to a file (`dart:io`, which keeps the
  party package on the web), each game's `hud.dart` layout and
  `hud_readout.dart`, `CryptRings`' choice of what gets a ring,
  `runnerPoses` and `GhostKeeper`'s per-circuit files.
- *River's HUD* is drawn by the game's own canvas layer, so it uses no
  HUD piece.
- *The showcase* still has its own `_ghostOf` (`sharing_ghosts.dart`); it
  can call `ghostOfRun`.
- *The physical camera* of `0.10-plan.md` B6.22 is not in photo mode yet.

**Behaviour that moved, knowingly.**

- The reels of hollow, reef and racing write their PNGs through the
  engine's encoder now: the same pixels, different bytes. Strategy's reel
  stops on a frame it could not write, rather than going on.
- The platformer's ending tallies are the shared `Wrap`, so they wrap on a
  narrow screen instead of overflowing; when they fit, they look the same.
- `ShareStrip`'s key is `share:open` (it was `share:race`).

**Tests to run** (written, not run): `test/` in each of the fourteen
packages (141 cases); then in the demos:

- dungeon: `photo_mode`, `reactions`, `soundtrack`, `ending`, `credits`,
  `cutscene`, `touch_crypt`, `first_shot_hint`, `high_contrast_rings`,
  `assembly`, `ragdoll_corpses`, `physics_backend`, `depths`,
  `run_terminal`, and the widget tests that build the loop (now with
  `SpokenEvents`);
- platformer: `photo_mode`, `reactions`, `soundtrack`, `sounds`,
  `title_card`, `ending`, `credits`, `lens`, `replay`, `share_ghost`,
  `touch_runner`, the HUD tests;
- racing: `photo_mode`, `reactions`, `ending`, `credits`, `touch_drive`,
  `ghost`, `looks`, `hud_label`, `stereo_hud_panel`, `party_race_session`,
  `net_race_session`, `net_race`, `net_race_screen`;
- sandbox: `photo_mode`, `frame`, `sandbox_run`; arcade and strategy:
  `credits` and strategy's HUD tests; reef and river: their staging and
  frame tests. The reels are run by hand with `-t lib/reel_main.dart`.

2. Post first: one family at a time, CPU goldens checked after each,
   none moving. *Families and preset done as switches (see Progress); the

   lose their own copies. *Done as fourteen packages (see Progress); the
   tests are still to run.*
