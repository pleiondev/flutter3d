# flutter3d 0.9 — what is left, and in what order

Written 2026-10-06, on branch `0.9.0`, after N1, N2, N3's authoring, N9's
colour vision and roles and N12's cutscenes landed. `0.9-engine-roadmap.md`
stays the record of what each item is and what was done; this is the order
the rest is done in, and what "done" means for each piece. Sizes are the
roadmap's: S a day or two, M a week, L more.

## 0. Where it stands

- **Done or nearly:** HR1–HR5 on desktop, P1–P10, N1, N2, N4, N5, N8, and
  the core of N3, N6, N7, N9, N10's format and N12.
- **Started, with no game using it:** behaviour trees (no game spawns one),
  telemetry and cloud saves (no game asks the player), sharing (no game
  shares), the time-travel debugger and render inspection (no MCP tools on
  them).
- **Not started:** N11 procedural generation, N13 voxels, N14 networking past
  two, H11 GPU splat sort, the editor's docking shell and web build (P11),
  the platforms of §6, and the 0.9.0 revision of the comparison page.
- **Pre-existing failures to clear before a release:** 48 modeller
  screenshot tests, the showcase's `catalog_test` (xpbd-cloth) and
  `bundle_test`. *Cleared 2026-10-06*: the screenshots differed
  only at glyph edges (and the new animation-graph panel), and were
  recorded again; `catalog_test` read `## 0.8.2+1` as `0.8.2`;
  `bundle_test` passes on its own.

Two rules from the last weeks carry on: a feature is not done until a game
uses it (N2's navmesh and N12's cutscenes found real bugs only once the
dungeon ran them), and every claim in a test is checked by a mutation that
breaks it.

## 1. Close the loops — features a game does not use yet (M each)

Order: the cheapest loop first, and anything that changes a recorded run
together with the re-recording it needs.

1. **Monsters run behaviour trees (N3).** *Done 2026-10-06.* The shooter's attack, chase and
   pain as leaf kinds (`attack`, `flinch`, the ChaseBrain states as leaves),
   so a `monster` entity with a `behaviour` property spawns a
   `BehaviourBrain`; one guard in a dungeon level authored as a tree; the
   `BehaviourOverlay` path and names drawn in the dungeon's debug view (the
   roadmap's "overlay in a demo"). *Done when:* a tree-driven monster
   fights like a `ChaseBrain` one in an A/B test, a restore mid-fight agrees
   bit for bit, and the overlay's names are on screen in a golden.
2. **Cutscenes authored, not only typed (N12).** *Done 2026-10-06.* An editor dialog over a
   `cutscene` entity (the document as text, refused with every problem, like
   Behaviours), the MCP `setCutscene` tool, and a preview that plays the
   camera path in the editor's viewport. *Done when:* an agent writes the
   sanctum's scene through MCP from nothing and the level validates.
3. **The flow field follows breaches (N2).** *Done 2026-10-06.* `NavGrid` rebakes the cells a
   hole changed, the way the navmesh does, so a chasing monster uses a
   breach too. *Done when:* the A/B test of the guard behind a wall passes
   for a chase as well as for a patrol.
4. **Saves the player is asked about (N6, N7).** *Done 2026-10-06.* The racing game is left off
   `Autosave` on purpose: its season is one sitting, and its settings say so. A consent switch and a
   "which run do you want" dialog in the shared settings panel; the dungeon
   and racing on `Autosave`; the platformer calling `SaveSync` before
   `begin`; telemetry's question in the same panel and a `JsonPost` over a
   real client. *Done when:* each game's settings show both questions, off
   on a fresh install, and nothing leaves the device until one is on.
5. **A game that shares (N10).** *Done 2026-10-06.* The platformer shares a run as a bundle and
   opens one by its short code; ghosts from pose tracks for the platformer,
   not only racing. *Done when:* a run shared from one window replays as a
   ghost in another against the reference server under `dart run`.

## 1½. Physics: the native core by default everywhere, Dart as fallback — L

Asked for on 2026-10-06. Every system that simulates physics — rigid
bodies, characters, rays and queries, vehicles, cloth, ragdolls, particles
that collide, the strategy and racing demos — runs on the C core (FFI on
native platforms, WASM in the browser) unless it is unavailable, and only
then on the Dart reference. One switch picks the backend for a whole run;
nothing chooses per system. *Done when:* every game and showcase page
stages through that switch, the default is the core on every platform it
builds for, the Dart path is exercised by the same tests run with the
switch flipped, and a run recorded on one backend replays on the same
backend bit for bit (the two backends are not promised to agree).

*Progress.*
- The switch:
  - `PhysicsBackend` lives in `flutter3d_physics`, and `NativePhysics`, `usePhysics`, `preparePhysics` and `startPhysics` in `flutter3d_physics_native`.
  - Whether the core works is tested by making a world. When it does not, the run falls back to Dart with a reason.
- The dungeon, platformer, arcade and the showcase's physics pages go through it. The dungeon's ragdolls exist only on the core; on the reference the dead play their death clips.
- `Demo.physics` is stamped on every recording. A replay test switches to the backend the tape was recorded on, and in-game replay refuses a tape from the other backend.
- The three games' suites pass under both `FLUTTER3D_PHYSICS` values.

- Every world a game steps is now on the run's backend:
  - `LevelLoader` attaches the backend to every level, and releases it on dispose.
  - Dynamics made for an attached world take it over.
  - The shooter's staging defaults to `shooterDynamics`.
  - `resimulate`, `sim_mcp`'s sessions and playtests, the modeller's Play, the racing game and its network race, and every showcase page that makes a world all go through it.
- Sweeps run on the core (`NativeWorldSweeps`), unless a sweep has a `ContactFilter`, so the racing cars and the platformer's runner sweep there.
- Recordings and replays:
  - `ascent.f3drun` and the site's samples were re-recorded on the core.
  - `sim_mcp` verifies a run on the backend it was recorded on.
  - The telemetry server replays a run on the backend it was recorded on (`choosePhysics` in the replay isolate). When that backend cannot be loaded, it refuses with `ResimulationOnOtherPhysics`. The server's build host now needs a C compiler for the core's hook.
- These suites pass under both values of the switch:
  - dungeon, platformer, arcade, racing, the modeller's Play, the showcase.
  - The showcase's only failure is the existing `xpbd-cloth` catalog entry.
- **Kept on the reference on purpose:** the lightmap and visibility bakes. Their output is committed, and must come out byte for byte the same on any machine.

*Next:*
- ~~Cloth with obstacles on the core.~~ Done:
  - `f3d_cloth_solve` matches `stepCloth`: wind, self-collision, and obstacles of every shape with friction.
  - `PhysicsBackend.cloth` returns `NativeClothSimulation` on the core and `DartCloth` on the reference.
  - The showcase's XPBD page and the modeller's cloth bake both use it.
  - The core stays within 0.5–2.4 mm of the reference on the test scenes.
- ~~Fluid.~~ Done: liquid, pipes and floating bodies step on the core.
- ~~A network race does not check that both peers are on the same
  backend.~~ Done 2026-10-06:
  - The relay takes `terms` on a room, a party and matchmaking. The first
    machine sets them, and a machine asking with others is closed with a
    reason that names both. Matchmaking keys on them, so strangers on
    different physics never share a party.
  - The racing game asks with `physics=<backend>`, taken from `usePhysics()`
    so the run's choice is made first. Read off `PhysicsBackend.current`, the
    first machine of a party said `dart` and the later ones `native`.
  - `WebSocketTransport.closed` carries the relay's reason. `joinParty`
    fails with it at once instead of waiting out the timeout, and the
    two-car race screen shows it instead of racing a ghost.
  - Tests: `relay_test`, `party_relay_test` and `net_race_test`, each
    mutation-checked.
- `flutter3d_physics_native` has to be published for 0.9.0, because `flutter3d_sim_mcp` now depends on it.
- `flutter3d_model_core` uses `ClothSimulation`, which is new in `flutter3d_physics`, so its constraint must be raised at release.

## 2. Agent tooling on what exists (P12, N4) — M

*Done 2026-10-06*, event subscription included: a game posts what happened
with `postGameEvent` (the dungeon posts a level loaded, the player died and
came back, a pickup taken, the way out reached and the run finished), Play
keeps it beside the console, and `play_events` reads it by cursor.

The game side is done; the MCP side is not.

- MCP tools over the render extensions: `list_draws`, `get_draw`,
  `list_passes`, `pass_output`, `read_pixel`, `scan_nan`, `render_stats`.
- `build`, `run`, `stop`, `hot_reload`, `reload_level` and event
  subscription, reusing the editor's `PlaySession`.
- Desync bisect between two `.f3drun` files as a tool (the library call
  exists), and dropping a tape the running game recorded into `test/tapes/`.

*Done when:* an agent, from a cold session, runs the dungeon, finds the draw
that paints a given pixel, and bisects two tapes to the first differing step
and component — each scripted as an MCP integration test.

## 3. Render work that needs all four backends — M each

Each lands off by default and is switched on only once its golden exists in
the Metal, Impeller, WebGL and software sets (decision 18). The software set
is recorded here; the other three need a run on hardware, so each item ends
with a list of goldens to record rather than a claim that they match.

1. **High contrast with outlines (N9).** An outline pass from the depth and
   normal buffers, a high-contrast look that flattens texture detail, and an
   accommodation that turns both on; actors and pickups outlined in the
   game's role colours. *Done 2026-10-06*: all four references agree pixel
   for pixel; the dungeon rings its monsters, pickups and keys.
2. **The physical sky and height fog on by default (P5).** One change that
   re-records every golden with a sky or fog, as the roadmap says. *Done
   2026-10-06*: `SkySettings.resolvedPhysical`, `FogSettings.defaultHeightFalloff`;
   `sky` and `orthographic-metal` re-recorded in all four sets.
3. **Decals, reflectors and render textures in the level format, the editor
   and MCP (P3, P4), and the debug views in the editor's viewport (P6).** *Done 2026-10-06.*
4. **GPU splat sort on WebGPU compute (H11).** Its trigger is met; it waits
   on WebGPU becoming the browser default (§4 below). *Done 2026-10-06*: a
   radix sort of the CPU's keys on compute writes the draw's index buffer;
   the order is the CPU's to the splat and the picture to the byte
   (`splat_sort_gpu_test.dart`), and every other backend keeps the CPU sort.

## 4. Platforms (§6) — alongside, M

- Windows and Linux runners for the demos and the editor; native sides of
  `pad_input` and `pointer_lock`; CI desktop jobs made required. *Done
  2026-10-06* as far as this machine reaches: the runners and the C++ are
  written and the mapping is tested in Dart, but the first compile of the
  XInput, Raw Input, joystick and GDK code is the CI desktop job's. On Linux it was then built in an arm64 container and the
  dungeon started under Xvfb; it draws on the fallback backend, because
  Flutter GPU is off on Linux and Impeller's GLES backend refuses shaders
  that read `gl_VertexID` (ARCHITECTURE §1).
- Android: the frame numbers on the Galaxy A55 committed and gated.
- ~~WebGPU as the browser default with WebGL2 as the fallback.~~ Done 2026-10-06. `backend_choice_web_test.dart` holds it in Chrome, run both ways.
- The editor's web build (P11 / HR5): documents without the disk, and the
  `ws://127.0.0.1` socket checked from the published address. *Done
  2026-10-06*; from a public `https` page Chrome holds the socket behind a
  Local Network Access prompt, which the attach dialog now warns of.

## 5. New features not started — L, one at a time

1. **N11, procedural generation.** *Done 2026-10-06* (see the roadmap's N11 progress). WFC over the crypt kit's tiles, erosion
   on `Heightfield`, `(seed, rules) → Level` in an isolate, a reachability
   rule built on the navmesh (a level whose exit no route reaches is
   refused), and MCP `generate_level`. First because it reuses the most:
   the kits, the navmesh, the validator and the editor's `generate`.
2. **N13, `flutter3d_voxel` and a sandbox demo.** Chunks, greedy meshing,
   collision against chunks through the native core, edits saved as deltas,
   and the navmesh's tile rebake following edits. *Done 2026-10-06*: the
   sandbox demo digs, builds, saves and runs on both physics backends.
3. **N14, networking past two.** *Done 2026-10-06* (see the roadmap's N14 progress): the racing screen makes and joins parties, and finds one among strangers. Rollback for 4–8 players, rooms, a relay
   and spectators from the tape; then the authoritative model over
   `PeerWire` and our snapshots (decisions 15 and 22). Last, because it is
   the largest and touches the most packages.

## 5½. What an audit found left (2026-10-06)

Asked for the same day: every 0.9 feature gets a showcase page of its own,
and the games take the new features up. Two read-only audits of the tree
found the following. The order is the order of work.

**1. Physics not built yet.** Every one of these was on the 2026-10-03 list
for 0.9.0.
- ~~Compound shapes: several shapes on one body.~~ Done 2026-10-06 (ABI 22,
  snapshot format 9). Up to sixty-four parts of any convex kind, a hull
  among them. Mass by volume, inertia by the parallel axis. Contacts are
  the parts' contacts, joined along the deepest one's normal, the way a
  mesh's triangles are. ~~A part whose normal turns more than eighteen
  degrees is dropped~~: since 2026-10-06 a pair has up to two manifolds, one
  a face, for compounds and meshes alike (snapshot format 13). *Left:* a
  third face at once, a box in a corner where three meet, still holds by
  two of them. The Dart reference has no compounds, as it has no hulls.
- ~~Breakable joints: a joint that lets go past a force.~~ Done 2026-10-06
  (ABI 23). A force and a torque per joint. It is checked at the end of the
  step, against what the last substep held, so it holds for the step in
  which it was overloaded.
- ~~Multibody chains (reduced coordinates).~~ Done 2026-10-06 (ABI 25).
  Fixed and floating bases, with fixed, revolute, prismatic and spherical
  joints, limits and motors. The joints are read off after the solver.
  The links are put back by forward kinematics, and their velocities are
  projected with (Jᵀ M J)⁻¹ Jᵀ M. *Left:* the links move freely within a
  step, so a contact the step resolved can be undone by the projection
  for that step. ~~No cone limit on a spherical link yet.~~ Cone done
  2026-10-06 (ABI 26), swing and twist, held on the turn and on the speed.
- A vehicle on the core: wheels as rays or joints with suspension and tyre
  friction. *Core done 2026-10-06* (ABI 24). Ray wheels with a spring and
  a damper. Tyres solved together through the chassis's mass and inertia,
  inside a friction circle. Steering, drive and brake per wheel. Since
  2026-10-06 the wheel's rim, cast as a cylinder, meets kerbs and planks the
  ray stepped over. *Left:*
  a car behind the racing game's `VehicleController`. The game's own car is
  still the kinematic sphere, and its recorded laps and ghosts stay on it.
- ~~The solver, broadphase and narrow phase on the GPU for game bodies, by
  graph colour.~~ Moved to 0.10 (the owner's call, 2026-10-06). The
  deterministic mode, which replays and the network depend on, could not
  use it; the browser has no GPU passes; and the games here step tens of
  bodies, not thousands. Visual bodies, cloth, fluid and particles already
  run there.

**2. Showcase pages missing.** A page per feature, tagged `0.9.0`.
- ~~Physics~~ done 2026-10-06, ten pages: `compound-shapes`,
  `breakable-joints`, `vehicle`, `multibody-chain`, `joints-and-motors`,
  `ragdoll`, `convex-shapes`, `continuous-collision`, `heat-and-fire`,
  `liquids`. Each page's `verify` is held by `pages_test`. *Left:* a page
  for the GPU systems (particles, debris, cloth, fluid), which the CPU
  device of the page tests cannot check. The heat page found that the core
  passed no radiation between bodies apart; since 2026-10-06 the core
  radiates between bodies and a fire's flame heats what stands in it, so a
  fire spreads from crate to crate, and the page no longer radiates its
  heater itself. *Left:* nothing shades radiation.
- Rendering: lens flare and distortion, and a real `.cube` file (P2); debug
  views and render stats (P6); per-draw ranges, alpha to coverage and draw
  order (P7); `.f3dmat` with a lighting hook, parameters and instance data
  (P8).
- Engine and tools: hot reload (HR1–HR4); the widget API (P10); render
  inspection (P12).
- Features: the animation graph (N1); navmesh and crowds (N2); behaviour
  trees (N3); the time-travel debugger (N4); replay tests (N5); saves (N6);
  telemetry and heatmaps (N7); photo mode (N8); daltonise, simulation, role
  remapping and the hue lint (N9's rest); sharing and ghosts (N10);
  erosion (N11's rest); cutscenes (N12); parties past two (N14).

**3. Games extended.** The audit's matrix, game by game.
- **racing:** photo mode; the physical sky; lens flare; a rear-view mirror

- **platformer:** the physical sky and stars, and height fog; the animation

**4. The editor's shell (P11).** Docked panels, an outliner, a component

## 7. If 0.9.0 has to be cut short

§10 of the roadmap names the natural cut: parity first. Here that means §1
items 1–3, §2, §3.1–3.2 and §6 ship as 0.9.0, and §5 moves to 0.10 — each of
N11, N13 and N14 is large enough to be a release's headline on its own.
