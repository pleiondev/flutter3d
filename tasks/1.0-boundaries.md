# Package boundaries before rc.1 (2026-10-09)

This is a read-only audit of all 53 packages. It compares what each package
claims to own (README, pubspec, ARCHITECTURE §3.2) with what it actually
exports (barrels, `api/*.api`).

## Findings

**Healthy:** there are no cycles, and sim, physics, core and plugin_api
carry no Flutter.

The leaks fall into three groups.

1. **Re-export facades hide real dependencies.**
   - `flutter3d_sim` re-exports about 85 physics symbols. About 230 files
     in 20 packages use physics only through sim; nine packages use physics
     types without depending on physics.
   - `flutter3d` depends on sim, physics and audio_core only in order to
     re-export them.
   - `flutter3d_game` re-exports all of `flutter3d`.
2. **Foundation value types live in the wrong homes.**
   - **plugin_api** has grown to 77 types. Not all of it is the plugin
     contract:
     - foundation: `WorldPosition`, `LinearColor`, the exception roots,
       `Issue`, the format envelope and `Registration`;
     - sim-host types: `SimulationHandle` and its kin;
     - empty marker registries.
   - **physics** has grown to 99 types: the vector crossings, `Portable`,
     `WorldProperties`, the material catalog (optics, acoustics, heat) and
     the constants.
   - Hardware, shaders and the backends depend on plugin_api only for
     exceptions and formats. audio_core and particles depend on physics
     only for `WorldProperties` and constants.
3. **Dependency inversions.**
   - `physics_native` → `core` (`SkeletonRagdoll`).
   - `core` → `physics` (`liquidMeshes`, `Portable`, the re-export of the
     crossings).
   - `app` (runtime) → `editor_core` (`LevelScene`, `LevelBatching`).
   - `plugin_runtime` knows about every subsystem's data section.
   - `effects` fuses the elements simulation with its views
     (`TrackedBody.look: SceneNode`, `WaterBody.view: LiquidView`).
   - `game` and `game_ui` duplicate each other: credits, touch widgets,
     automap/minimap.
   - Duplicate names: `Brush`, `LevelValidator`, `Particle`, `OpenKind`,
     `AddLight`, `MoveBy`, `Listed`.

## Target map (layers; each package depends only on layers below it)

- **L0:** `flutter3d_foundation` (new): `WorldPosition`, `LinearColor`,
  exceptions, `Issue`, `FormatSpec`/`FormatDocument`, `Registration`,
  `Portable`, the vector crossings. It depends only on vector_math.
- **L1:** `plugin_api` holds the plugin contract only and re-exports
  foundation. `hardware` → foundation.
- **L2:** `flutter3d_matter` (new): `WorldProperties`, `PhysicalMaterial`,
  `MaterialCatalog`, the standard atmosphere and the constants.
  `shaders` sits here too.
- **L3:**
  - `physics` → matter;
  - `audio_core` → matter;
  - `core` → hardware/shaders/plugin_api, with no physics;
  - the backends.
- **L4:**
  - `physics_native`, with no core;
  - `sim`, with no re-exports of physics;
  - `particles`.
- **L5:**
  - `flutter3d_elements` (the simulation, split out of effects);
  - `effects` (the views);
  - `flutter3d_level_scene` (`LevelScene`/`LevelBatching` out of
    editor_core);
  - `flutter3d` (the shell over core, with no re-exports of
    sim/physics/audio).
- **L6:** `app` and `editor_core` both depend on `level_scene`.
- **L7:**
  - `game`: the one game facade, which deliberately re-exports chosen sim
    entry points;
  - `game_ui`: every widget;
  - the kits and the genres.

## Rules (`tool/structure`)

1. An allowed-dependency matrix per package (`layers.dart`).
2. No dependency used only for a re-export.
3. An allowlist of cross-package re-exports, each with a reason.
4. Declare what you name: if a type from package X is used, X is in the
   pubspec.
5. plugin_api: every type is reachable from the contract's signatures;
   there is a type budget; no `LoopPhase` belongs to a single package.
6. The simulation stack (sim, physics, physics_native, elements, matter)
   imports no core, hardware, shaders or particles.
7. The runtime (app, game*, genres, effects, audio) does not depend on
   editor_*, build, mcp or model_core.
8. A public name has one home across all packages.
9. `internal.dart`, `builtin.dart` and `testing.dart` are imported only by
   an allowlist.

## Decisions (Dmitrii, 2026-10-09)

1. **Both new packages,** `flutter3d_foundation` and `flutter3d_matter`
   (moves 1, 2, 3). plugin_api and physics keep re-exporting during the
   move.
2. **Remove the re-exports now** (moves 10, 11). The only intentional
   facade is `flutter3d_game`, with an explicit list. A rule forbids new
   re-exports.
3. **Split effects** into `flutter3d_elements` (the simulation) and
   `flutter3d_effects` (the views) (move 8).
4. **Everything else in the plan is done**, together with all 9 rules.
