# Taken into 1.0 from 0.10 (decided 2026-10-08)

Dmitrii chose these after the plugin model, addons and stability work had
landed. Each passed one of three tests:

- After 1.0, it would need a major version.
- It changes a default picture or behaviour, which after 1.0 needs a
  minor version with a flag back to the old one.
- It finishes something half-done in this cycle.

All of it lands before `1.0.0-rc.1`. The plan item numbers refer to
`0.10-plan.md`.

## Finishing what was started

1. **Typed settings slots in `RenderSettings`.** The addons then own their
   settings types, with core forwarders as a non-breaking bridge.
2. **The registries wired into the apps.**
   - The editor app and the MCP servers create the registries and install
     plugins.
   - The demos install `ReactionsPlugin` and `SoundtrackPlugin`, and
     `SpokenEvents` where it fits.
3. **Replays everywhere.**
   - Every demo records through `DemoRecording.attach`, so loop journals
     and event digests go into the run files.
   - Hollow, Reef, Water and the sandbox record and replay.
   - The strategy genre gets a `HeadlessGame`.
4. **An effects description format.** A declarative particle and VFX
   document, versioned, with fixtures. `.f3dplugin` already refers to it.
   Plugin materials also get a WGSL runtime path on WebGPU. *Done, tests not
   run yet:* `.f3dfx` (`EffectDocument`, `f3dfx` 1, fixture
   `flutter3d_particles/test/fixtures/v1/blast.f3dfx`) and `ParticleEffects`;
   the dungeon's blast, torch, splash, splinters and sparks are written in it
   (`apps/flutter3d_demo_dungeon/effects/`) and held to their Dart particle
   for particle. Collision against depth is read and reported unsupported;
   a plane is what the CPU simulation does. WebGPU materials at run time are
   spliced into the compiled `Unlit` stage; lit materials, `instance` and
   maps beyond the base colour still come from the build.

## Defaults that change the picture

5. **Reversed-Z with a fitted near plane**, and an infinite far plane
   (A2.8–10). This also addresses the near cascades' 0.18 m shadow floor.
   *Code done*: `RenderSettings.reversedDepth` (on; off is the old
   picture), `DeviceFeature.reversedDepth` on Impeller with a float depth,
   WebGPU with `depth32float-stencil8`, WebGL2 with `EXT_clip_control` and
   the CPU; `PerspectiveProjection.infinite`, `withDepthPlanes`,
   `toReversedDepth`, `PassContributor.boundsFor`; the sun's map turned
   round, 32-bit where the device allows, its floor per fragment
   otherwise. Goldens to re-record (`0.9-release.md`), tests to run.
6. **Materials at mediump and no `discard` on the opaque path**, with an
   LOD cross-fade (A1.1–3). *Code done*: opaque variants of the six lit
   models and a depth pre-draw for masked, hashed and cross-fading draws;
   `LodGroup.crossFade` (a tenth by default, nought is the pop) and
   `MeshNode.lodFade`; `F3D_MEDIUMP` in the twelve material stages, with
   highp the default inside them and mediump only where `PRECISION.md`
   says it is safe, and `WebGlDevice.open(highpMaterials: true)` as the
   switch back. The A55 and browser frame times are still to take.
7. **A physical camera.** Exposure in EV from the physical sky's real lux,
   and photo mode with aperture, shutter and ISO (B6.22). *Code done, tests
   not run yet:* `PhysicalCamera` (aperture, shutter, ISO, compensation,
   `ev100`, `forSky`/`metered`/`atEv100`), `RenderSettings.camera` and
   `physicalCamera` (on; off is the multiplier alone), `cameraExposure`,
   `PhysicalSky.illuminance`/`illuminanceLux`, `FrameResult.ev100`; the
   default camera, f/4 at 1/60 s and ISO 100, is the reference and exposes
   exactly 1.6, so no golden moves. One unit of luminance is 1843.2 cd/m²,
   of illuminance about 5790.6 lux. Photo mode's keys 1–6 turn the dials and
   hand the aperture to the depth of field.
8. **Clustered lights on by default** (A6.28). *Code done*:
   `clusteredLights: false` is the flag back. The suite's two scenes with
   more than eight lights already asked for the cells, so no golden moves.

## API shape fixed before the contract

9. **The whole `.f3dmat` language** (A3.12–15), plus full-screen stages
   for plugin render steps:
   - a vertex block, also used in the depth and shadow passes;
   - ambient and composite hooks;
   - state in the file;
   - scene depth and position.

   *Done, tests not run yet.* The language is now version 2
   (`materialLanguageVersion` 2), and v1 files read and compile exactly
   as before. Version 2 adds:
   - `state {}`;
   - `vertex {}`, which the depth, shadow and pre-draw passes also use;
   - `ambient {}` and `composite {}`;
   - `sceneDepth`, `viewDepth` and `scenePosition`;
   - `fullscreen Name {}` and `compute Name {}`. Compute runs only on the
     CPU backend; the GPU backends refuse it.

   Backend support is in
   `site/content/reference/material-language.md`. The one break is
   `MaterialOutput`, which has a manual migration entry.
   Item 22 is done with it: `generateMaterialAccessors` writes
   `lib/materials.g.dart`, and the effects looks use it.
   - **Tests:** the new ones are `material_language_v2_test` (21) and
     `material_accessors_test` (3). No goldens exist yet for a moved vertex
     stage, a depth-layer decal or a scene-depth soft edge.
10. **An open registry of lighting models**, so toon becomes an addon.
11. **Virtual cameras** (D4). The genres' cameras move onto them.
12. **Prefabs with nested overrides, and depth layers, in the scene
    format** (D1, A2.11), both in the format's first version.

## Performance and platforms

13. **Frame pacing** (A1.4–7): frames in flight, an FPS cap, warm-up in
    slices and pipeline-stall reports. *Code done, tests not run yet:*
    `Renderer.pacing` (`FramePacing`: frames in flight one to three, a held
    frame when the GPU is behind, `heldFrames`), `PipelineStall` on
    `FrameResult.pipelineStalls`, `RenderListener.stalled`/`held` and the
    bus, `Renderer.warmUpInSlices`; `FrameCadence` with
    `EngineLoop.frameAtVsync`, `SceneSurface.cadence` and
    `Scene3D.frameRateCap`.
14. **Textures on the web** (A4.16–18): decoding by the browser with GPU
    mips, a size cap, and revalidation of the shader cache.
15. **Debugging and memory** (A5.21–24): debug channels, a two-channel
    wipe, frame capture to JSON and back, and a memory report.

## API foundations (second round, 2026-10-08)

All of these go into 1.0.0-rc.1, so that the 1.0 contract does not have to
be broken for years.

16. **Fewer packages.** About 70 packages become a smaller set grouped by
    meaning. For example, the 14 game addons become 3–4 packages, and
    users reach the public surface through a few facade packages.
17. **World positions in double precision.** The renderer draws relative
    to the camera. This means `vector_math_64`, or types of our own, in
    world-space APIs.
18. **Moving the origin.** The world announces an origin shift, with an
    event and hooks for physics, particles and lights. Chunks come later.
19. **A boundary between simulation and view.** The view reads the
    simulation only through state published in the `publish` phase, so
    that the simulation can move to an isolate later without a break.
20. **One ownership model for resources.** Handles with reference counts
    and an explicit `dispose`, ready for streaming. A structure rule
    catches leaks in tests.
21. **One exception hierarchy.** A root `Flutter3dException` with sealed
    families: format, capability, plugin, resource. `Error` is kept for
    programmer mistakes.
22. **Typed material accessors.** The `.f3dmat` build generates them. The
    string map stays for data plugins.
23. **Action maps for input.** Actions with bindings for keyboard,
    gamepad and touch, rebinding and saving. Replays record actions, and
    the genres move onto them.
24. **An audio model.** `AudioListener` and `AudioEmitter` in the scene,
    mixer buses and snapshots. HRTF and sound propagation arrive later
    behind the same API.
25. **One `Flutter3dView` widget on `EngineLoop`.** It owns the loop, the
    device, the plugins and the input, so a first scene takes about ten
    lines. `SceneSurface` stays as the low-level layer.
26. **A view is an object.** One world, several `RenderView`s, each with
    its own camera, target, settings, shadows and TAA history, sharing
    resources. Stereo and the editor move onto them.
27. **The game model.** The simulation is ECS with `EngineLoop` systems.
    The view is the scene graph, built from published state.
28. **A naming audit before rc.** American spelling in API identifiers,
    as Flutter and Dart use; the docs may stay British. Consistent verbs
    (dispose/close, create/open), and units in names. A structure rule
    keeps it.
29. **A units contract.** SI, Y up, a right-handed frame, radians and
    linear colour, written into the 1.0 contract. Every numeric parameter
    names its unit in its doc, which a rule checks.
30. **A codec for every simulation component.** Each one is versioned and
    used for snapshots, the network, prefabs and the editor. A rule and
    conformance enforce it, and a generator may write the codecs.

31. **Migration of user code from 0.8.x to 1.0.0-rc.1** (asked for on
    2026-10-08). `dart run flutter3d_build:migrate` runs analyzer-based
    codemods driven by a versioned migration table, plus `fix_data.yaml`
    for `dart fix`. **Rebuilt on the Dart tooling (Dmitrii, same day),**
    in three layers:
    1. `lib/fix_data.yaml` in each package, generated from the table. Users
       run `dart fix --apply` after upgrading, and the IDE shows quick
       fixes.
    2. Rewrites too complex for data-driven fixes become diagnostics with
       quick fixes in the `flutter3d_lints` analyzer plugin.
    3. A thin `migrate` command only for pubspec bumps, package
       renames and cross-package import moves, which then runs
       `dart fix --apply`.
    - **Seed.** The API snapshot diff between v0.8.5 and the current tree.
    - **Rule.** A new structure rule requires a migration entry, or a
      "manual" entry with guidance, for every break.
    - **Proof.** The 0.8.5 demos are migrated and must analyse clean.
    - **Every wave adds its own entries.** The final pass runs after
      wave 4, once the names are final.

32. **One `flutter3d` command, and assets from other tools** (asked for on
    2026-10-08). `flutter3d` in `flutter3d_build` runs `convert`,
    `create`, `init`, `plugins`, `migrate`, `lights` and `doctor`; every
    `dart run flutter3d_build:<name>` stays. `convert` reads glTF, OBJ,
    STL, PLY, USD, MaterialX, Unity and Godot text assets, and FBX and
    `.blend` through external tools, into `.f3d`, `.fmat`/`.f3dmat` and
    level documents with prefabs, with a report per input. *Code done,
    tests not run yet:* `lib/src/convert/`, `lib/src/doctor.dart`,
    `lib/src/project_template.dart`, `bin/flutter3d.dart`; fixtures under
    `flutter3d_build/test/fixtures/convert/`; `convertFiles` in
    `package:flutter3d_build/convert.dart` for the cloud service;
    `ModelVisuals` reads a row's `tilt` and `scale`; the site page
    "Bringing assets in".
33. **`.f3d` as a whole asset** (asked for on 2026-10-08). One file carries
    the model, its lights and cameras, each material's lighting model, the
    `.f3dmat` programs a material names, the scene as level documents with
    prefabs, and any other file a prefab names (a scene's models, `.fmat`,
    textures). Optional sections 29–35, none must-understand and no version
    bump: an older reader opens a poorer asset, never a different one.
    `flutter3d convert` writes one `.f3d` per input by default, and
    `--split` keeps the separate files. *Code done, tests not run yet:*
    `F3dWriter(programs:, prefabs:, files:)`, `F3dDocument.programs`,
    `prefabs`, `files`, lights and cameras through `ModelDocument`;
    `f3d_writer_bundle.dart` and `f3d_loader_bundle.dart`; the fixture
    `flutter3d_core/test/fixtures/v2/bundle.f3d`; `lib/src/convert/bundle.dart`
    and `convertFiles(bundle:)` in `flutter3d_build`; the site's asset
    pipeline and "Bringing assets in" pages.

## Waves, so that no two agents edit the same files

The order is now:

- **Wave 1 (disjoint areas):** depth and precision (5, 6); apps, editor
  and servers (2, 3); effects format and WebGPU at run time (4); virtual
  cameras (11); the audio model (24).
- **Wave 2:**
  - render settings slots and lighting models (1, 10);
  - the material language with typed accessors (9, 22);
  - frame pacing, defaults and the physical camera (7, 8, 13);
  - the scene format with prefabs (12);
  - textures on the web (14);
  - debugging (15);
  - action maps (23).
- **Wave 3 (cross-cutting):**
  - double positions, origin shift and the sim/view boundary with ECS
    (17–19, 27);
  - views as objects with the widget (25, 26);
  - codecs (30), ownership (20) and exceptions (21).
- **Wave 4 (mechanical, last):** the naming audit and units contract (28,
  29), then fewer packages (16).

The API review of 2026-10-08 (`1.0-api-review.md`, with decisions) widens
waves 3 and 4. Wave 3 now runs in this order:

1. **The foundation.**
   - What it adds, in `flutter3d_plugin_api`, which has no dependencies:
     - `Flutter3dException` and its families;
     - `WorldPosition`;
     - `LinearColor`;
     - the rules for base classes.
   - The `vector_math` conversions go into `flutter3d_physics`.
   - Alongside it runs 3d, the game layer: demos into `flutter3d_samples`,
     `GenrePlugin`, `ActionMap` as the only input model, localisation,
     save slots, and `ValueListenable` in place of the cubit.
2. **In parallel:**
   - 3a: simulation and view, ECS, network, plugin versions;
   - 3b: `RenderView`, `Flutter3dView`, one render step node, the HAL on
     base classes, photometric units;
   - 3c: formats with the envelope and ids, wire names, MCP, VM and the
     CLI.

The original wave notes follow.

- **Wave 1:**
  - 5 and 6 (shaders, projection, backends);
  - 2 and 3 (apps, editor, servers);
  - 4 (particles, plugin runtime, WebGPU runtime shaders);
  - 11 (a new addon and the genres' cameras).
- **Wave 2:**
  - 1 and 10 (render settings, material lighting);
  - 9 (material language, build, translators);
  - 7 and 8 together with 13 (renderer pacing and defaults);
  - 12 (scene format, editor);
  - 14 (web textures);
  - 15 (debugging).

After both waves come the tests, then re-recording of the tapes and every
golden set, which moves with 5–8, and then the release candidate.
