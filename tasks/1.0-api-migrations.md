# The API breaks and their migrations before 1.0.0-rc.1 (2026-10-09)

`1.0-rc1-plan.md` orders the work in waves. This document adds two things
to it. First, the order of the API breaks inside waves 2 to 3 and, for each
break, how a user's code and data move across it. Second, a wave **M** that
puts the migration tools in shape before wave 2 begins. It changes none of
the rc1-plan items. Where it adds work, the item names its owner from there.

## Where the tree stands (branch `1.0.0`, d3f905a56)

- Wave 2 has not started. The seven `@Deprecated` are all still present. The
  eight enums of A5 are enums and the four `sealed` types of A4 are sealed,
  and the snapshots hold 45 `sealed class` lines. `WebGlDevice.open` is
  synchronous and `GpuRenderBackend.open` takes no size. `TimeSource`, the
  `*Options` groups, `PluginGroup`, `MaterialParameters`, `SimulationProfile`
  and `EngineLog` do not exist. Foundation has `LinearColor` and the exception
  roots but no `ShaderCompileException` or `AssetNotFound`.
  `UnsupportedCapability` is in hardware.
- The migration machinery works. `0.8_to_1.0.yaml` has 1 538 entries:

  | kind | entries |
  |---|---|
  | manual | 721 |
  | rename | 286 |
  | none | 265 |
  | moved | 103 |
  | parameters | 66 |
  | import | 55 |
  | implementsToWith | 23 |
  | rewrite | 19 |

  The generator writes 614 fixes into 40 `fix_data.yaml` files.
  `generate_migrations.dart --check`, `migration_seed`, 56 snapshots and
  `tool/migrate_corpus.sh` are all in place.
- Two holes:
  1. `flutter3d migrate` rewrites Dart and pubspecs only. Levels, `.f3d`,
     `.f3dmat` and tapes are lifted when they are read and never on disk.
  2. 384 of the 721 manual entries say the same thing: the symbol was a
     backend's own and is not exported since 1.0. That covers cpu 167,
     webgpu 149, impeller 45, webgl 14, and 9 elsewhere. These entries make
     the guide read as "721 places by hand" when about 337 are real.
- Of the seven deprecated names, only `agxFull` has an entry. The other six
  get theirs when they are removed (step 2.0).

**The contradiction settled.** The wave 3d decisions of the API review make

gets a "superseded" line.

### Step 2S: growing enumerations (2026-10-10)

S0 of `1.0-seams.md`: a value added to a public `enum`, or a subtype to a
public `sealed` class, breaks every exhaustive `switch` written against it,
so it cannot come in a 1.x minor. Every such type in `api/*.api` was decided
one by one, re-exports counted once: **126 types, 92 enums and 34 sealed**
(the 108 and 39 counted at 2Z were lines, a type declared in two libraries
of one package counted twice).

| Decision | Enums | Sealed | Shape |
|---|---|---|---|
| Open | 74 | 22 | an enum becomes a `final class` with `static const` members and a private constructor, `values`, `name`, `byName` (null for an unknown word) and the enum's `toString`, as `DeviceFeature`; `index` where code read it. A sealed result or command becomes `abstract final`: only its package adds a case, and no `switch` outside is exhaustive |
| Visitor | — | 1 | `TextureNode`: `abstract base class` with `accept` and a `TextureNodeVisitor` whose `visitUnknown` answers for a kind it predates |
| Visitor, pending | — | 2 | `MaterialStatement`, `ResourceSize`: D24 in step 2.2 converts them; `closedSetPending` holds them until then |
| Closed for good | 18 | 9 | stays an enum or sealed, and its doc says why no member can be added |

**The test for closed.** A type is closed for good only if no member can
ever be added without changing what the type means: a direction, a sign, the
answers of a yes or a no, a fixed mathematical set, a specification's frozen
list with its own version. Everything that names a kind, a tier, a reason, a
phase, a mode, a refusal, a placement, a backend, a format or a policy is
open. That reverses some earlier reasons on purpose: the `boundaryEnumExempt`
entries that called a mirror of `flutter_gpu` or a document key machinery
(the thing mirrored grows), and two sealed types the API review's wave 3d
kept sealed, `RunStatus` and `StrategyOrder`. `CloudFetch`, `CloudPut` and
`ScrubAnswer`, which it kept sealed too, stay closed: each is the yes, no
(and unknown) of one question.

**What changed in the code.** Every `switch` in the repository over an opened
type gained a wildcard, and none is silent: a backend's refuses the value by
name (`UnsupportedError('WebGPU has no blend factor for …')`), an internal one
throws `UnsupportedError` naming the value, and where a sensible answer
exists it gives it (a wire writer writes the value's `name`, a label shows
it, a command answers `Outcome.refused`, a pose skips a path it has no slot
for). Serialized names did not move: each open class's `name` is the
identifier its enum had, and the explicit wire tables (`project_wire.dart`,
`f3d_wire.dart`, `.fmat`) are unchanged.

**The rules.** `a public enum or sealed type is decided` reads the snapshots
and fails on an enum or sealed type in neither `closedForGood` nor
`closedSetPending`, on one `openedSets` says was opened, and on stale entries.
`no package at 1.x names a type of one at 0.x` (S6) reads the pubspecs and
the snapshots: a 0.x dependency behind a 1.x package's own types is allowed,
one named in its API is not. `flutter3d_game`'s input now names its own
`PadDevice`, `PadReading`, `GamePadButton`, `GamePadAxis` and
`MouseCapture`, with three `manual` entries on the allowlist
(`2s-game-PadInput-device`, `2s-game-PadPresses-menuButton`,
`2s-game-DesktopInput-capture`): an argument whose type moved is one no kind
rewrites. The owner confirmed the reopened wave-3d types and `abstract
final` for the opened hierarchies (2026-10-10).
`boundaryEnumExempt` lost its stale entries and its package-wide exemptions,
and now fails on an entry whose enum is gone.

**Migration.** 77 `enumToClass` entries (`2s-*-open`) for the 62 enums and 15
sealed types that existed at 0.8.5: a constant keeps working, and a `switch`
that named every case gains a wildcard with a TODO. The other 20 were born
after 0.8.5 and need none.

## The formats: one version per format per candidate

Nobody outside sees a version between two candidates, so each format moves
at most once per candidate. The wave that bumps it reserves the fields later
waves fill, and those fields are optional.

| Format | Version | Bumped by | Contents | Filled later |
|---|---|---|---|---|
| Level | v5 | 2C | `LinearColor` colors, `world` and `renderSettings` as patches, `behaviour` → `behavior`, `gravity` gone | `geoOrigin` and material ids, reserved in v5; 3F fills them without a v6 |
| `.f3drun` | +1 | 1A | `changedAt` | `ProbeReading` and external frames from 3F |
| `.f3dmat` | — | 3.0 | `version` and `updates` (D45); v1 and v2 read as before | — |
| `.f3d` | no bump | — | section 36 `physicalMaterials` is optional and skipped by old readers | — |
| `f3d.pipeline`, `f3d.experiment` | v1 | at birth | — | — |
| Shader bundle (F3SB, `.f3dshaders`) | v2 | AF3 | a stage's header holds its `ShaderStageKind` code where v1 wrote 1 for a fragment stage and 0 for the rest; v1 read as before (`test/fixtures/v1/`, `v2/` in `flutter3d_hardware`) | — |

Each bump comes with:
- a fixture under `test/fixtures/v<N>/`;
- a step in the `lift` chain;
- a line in the `migrate --data` report;
- a row in the guide.

- **`WebXrSession` (5G, `flutter3d_stereo` with the web backends' XR

**Velocity from a material's vertex block (2.2's seam, moved to rc.2).**
The gap in rc.1, written rather than hidden: the object-velocity pass draws
every node through the engine's `Velocity*Vertex`, so a `vertex` block that
moves geometry (a flag, water, wind in grass) gives the node's rigid motion
only. Temporal anti-aliasing ghosts it, motion blur misses it, and a stage
reading `velocity` reads the rigid answer. What rc.2 adds:

- `VertexStageVariant.velocity`, a constant of the open set, and
  `<name>VertexVelocity` (with its `Skinned` and `Instanced` halves) emitted
  from the same `vertex` block evaluated twice: at this frame's model
  transform and parameter values, and at the previous frame's. The stage
  writes the two clip positions the velocity stages already pair.
- The previous values: `MaterialParameters` keeps the frame before's
  floats when the renderer asks it to (a snapshot taken as the velocity
  pass runs, so a `time` uniform moved in place is seen at both), and
  `MaterialVertexInfo` appends `previous_view_projection` after
  `view_projection`.
- The velocity pass draws a material that lists the variant through it,
  and the engine's stage otherwise, as the depth passes do now.

What rc.1 already freezes so this is additive: `VertexStageVariant` is open;
`velocity`'s encoding is in CONTRACTS ("Frame resources a stage reads");
`MaterialVertexInfo` is the material language's own block, and a member
appended after the existing one moves no offset. No output is added to the
`vertex` block, since the variant evaluates the block the source already
has.

- A law kind of a plugin's own is a subclass with its `kind` on the wire;

| 2.0 | **`Unit` / `Quantity` in foundation, a vector of SI dimension exponents.** D39's parameter schema, D33's expression language, `Probe` (3F) and `PropertyLaw` (3A) all use this one type. 2B creates its schema before 3.0 creates the language, so the type has to come first. `ShaderCompileException` carries `stage`, `target`, `line`, `column` and an `excerpt`, or a list of such diagnostics. | a simulation graph typed by units; shader errors a tool can point at |
| 2B | `ResourceCache` / `MemoryBudget`: a live handle's priority can change, the budget has categories, and a load can be cancelled. `RenderSettings.telemetry` records typed per-node and per-resource entries, not strings. `MaterialParameters` overrides per node instance, not only per material. | a streaming scheduler; frame capture and Perfetto export; materials that change per object |
| 2D | `ElementFields` gets default bodies (principle A.1) and access by quantity (`quantityOf(body, Quantity)`, `addQuantity`). | pressure, humidity and concentration as fields, without breaking implementers |
| 2E (rule in 3F) | `SimulationProfile` carries capabilities (`isBitExact`, …). The determinism rule checks the capability, not `== deterministic`. | further profiles in 1.x |
| 2F | A test fixes how `Scene3D` reconciles: identity by key/id, no reload on rebuild, and nodes that disappear are released. `@visibleForTesting` comes off `HotSwap`'s public signature (A.5). | asset and `.f3dmat` hot reload on a contract that holds |
| 2.2 (2X) | Nothing new. D20, D22, D22b and D37 are kept whole, and D37's node kind stays open. `SceneBinding` maps a component field to a `ParameterKey` (also in `.f3dplugin bindings:`). A plugin's vertex stage outputs the previous position for velocity (*moved to rc.2, 2026-10-12:* see "Velocity from a material's vertex block" under the contracts rc.1 lands without an implementation). | decals, multi-view, compute steps, volumetrics from fields, temporal reconstruction |
| 3.0 (3E0) | The units of D33 are the `Unit` of 2.0. | — |
| 3.1 (3A) | **`PropertyLaw.at(MaterialState)` instead of `at(T, p)`.** `MaterialState` holds T, p and phase plus an open set of quantities (humidity, wavelength, concentration, char). `confidence` is an open class with wire names, and a value may carry an optional interval. | living materials, chemistry, weather, uncertainty |
| 3F | A `Probe` region is an open class (point, section, body, later volume). A `ProbeReading` may carry a field (shape, `Float32List`, unit) that crosses the isolate as `TransferableTypedData`. `ExternalStateInput` and `ProbeReading` carry `kind` (measured, estimated, predicted) and `quality`. The relay gets its own namespace for engine messages, and the observer path names a snapshot full or delta, with a per-receiver filter. | volume probes and fields; a twin's data contract; network deltas and interest management as minor protocol versions |
| 4E | `f3d.experiment` v1 reserves `unknowns:` (parameter, range, prior) and `observations:`. | inverse physics over experiments |

**Not on the roadmap:**
- **Neural physics.** It contradicts bit-exact determinism, and Impeller has no compute.
- **A spectral colour path in the public API.** Colour is `LinearColor` (decision 11). Measured BRDF tables inside a lighting model remain possible.

**Kept out of the core, as separate packages if ever:**
- MPM granular media, GPU particles and meshlets. Their gain is on WebGPU only.
- Ecosystems and a spectral reference renderer.
- A two-way thermo-hydro-structural coupling inside the C core. It would put the bitwise parity of P3 at risk.

**After 1.0, first:** a "reactive lab" slice on hooks that will already
exist: living materials, physics-to-audio, branching worlds.

### The 1.x additive backlog (2026-10-13)

From the comparison of the extension surface with other engines. Each is
additive under the rc.1 contract and waits for a minor; none is rc scope.

1. Kernel language growth: uniform blocks, atomics, workgroup memory and barriers, float and 3D storage images, subgroups (each behind `kernel <N>`).
2. `PassContributor` in shadows, the depth prepass, velocity and picking: empty-bodied members on the `base` class.
3. Custom vertex attributes in `.f3dmat` (`attribute float stress;`) and packed vertex formats, in a later `f3dmat N` with a variant.
4. Material functions and includes (`use`, `fn`) and bounded loops in a later `f3dmat N`, gated by `since`.
5. Field inputs (`field density = acme.density;`) and 3D textures in materials (`MaterialTextureSlot` gains a `dimension:` with a 2D default).
6. Scene redraw with a layer mask and a lighting-model override: named `layers:`/`override:` on the `final` `SceneEncodeRequest`.
7. Graph-owned transient buffers (`FrameGraphBuilder.createBuffer`) and an optional access kind (`usage:`) on each read and write.
8. Required GPU features in the plugin manifest (`requires: Set<DeviceFeature>`), refused at install with a sentence.
9. Light extensions: a per-light extra texel (`lightExtra`: IES, cookies, tubes with a radius) and shadows for plugin light types.
10. Mobile tile memory: framebuffer fetch as a `DeviceFeature` and a stage input, memoryless transient attachments where a target never leaves its pass.
### The hardware layer's additive list (2026-10-13)

A comparison of `flutter3d_hardware` with the other graphics abstractions
(WebGPU, wgpu, bgfx, sokol, SDL_GPU, Diligent, NVRHI, Filament, Godot's
RenderingDevice, Unreal's RHI) found no gap a 1.x minor cannot fill. Before
rc.1 the pipeline descriptor (`PipelineDescriptor`,
`ComputePipelineDescriptor`, `createPipelineFrom` and its twins), the
per-axis border (`SamplerAddressMode.clampToBorder`), the frozen
pipeline-statistics stride and the trace targets as classes landed. What
stays for 1.x, each without breaking an outside backend. Mechanisms: **M** a
member with a default body (a refusal by feature, or a no-op where it is a
courtesy), **F** an optional descriptor field asked for by that descriptor's
`checkFeatures`, **DF** a new `DeviceFeature` or a reserved one promoted,
**V** a constant of an open class.
