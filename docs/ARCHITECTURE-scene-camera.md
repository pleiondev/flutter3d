# Сцена и камера: разбор моделей и предложение

Дата: 2026-08-08. Статус: решение принято и реализовано (см. §8-9).

---

## 1. Что не так сейчас

Текущее состояние (после glTF-декодера) честно описывается так: **сцены нет**, есть
плоский список draw-вызовов, а камера захардкожена внутри рендерера.

Конкретно:

| Проблема | Где | Почему это тупик |
|---|---|---|
| Камера вычисляется внутри `render()` | `mesh_renderer.dart` | Нельзя ни подвигать её пользователем, ни иметь две камеры, ни отрендерить в текстуру для отражений |
| Вращение модели зашито в рендерер | `spinMatrix` в `render()` | Анимация — свойство сцены, а не рендерера. Сейчас нельзя вращать один объект из двух |
| `GpuModel` — плоский список | `gpu_model.dart` | Нет иерархии: узел glTF, двигающий поддерево, не выражается. Трансформы уже «схлопнуты» на этапе загрузки |
| Нет отбраковки и сортировки | — | Всё рисуется в порядке списка. Прозрачность не заработает, а пайплайн переключается сколько угодно раз |
| Свет — константа в шейдере/uniform'е | `render()` | Свет не объект сцены, его нельзя двигать и нельзя иметь два |
| Один проход, одна цель | — | Тени, пост-обработка и multi-view требуют «камера + цель + фильтр» как отдельной сущности |
| Модель = ассет = экземпляр | `GpuModel` | Нельзя поставить одну модель в сцену дважды с разными трансформами, не загрузив её дважды |

Последний пункт особенно показателен: glTF-декодер уже умеет переиспользовать меш
между узлами, а `GpuModel` это преимущество теряет.

## 2. Как это решено у трёх библиотек

### three.js — единый `Object3D`

Одна базовая сущность с трансформом и детьми; `Mesh`, `Camera`, `Light` —
её наследники.

- Ленивое обновление через грязный флаг: изменение `position` не пересчитывает
  матрицы, а ставит `matrixWorldNeedsUpdate`. Раз в кадр `updateMatrixWorld()`
  обходит дерево, считает `matrix` из TRS и `matrixWorld = parent.matrixWorld × matrix`.
- `matrixAutoUpdate` / `matrixWorldAutoUpdate` позволяют отключить автоматику
  для статики.
- `layers` — битовая маска каналов, `visible`, `frustumCulled`, `renderOrder`.
- `attach()` — перепривязка с сохранением мирового трансформа (в отличие от `add()`).
- Рендерер каждый кадр собирает render list, делит на opaque/transparent и
  сортирует: непрозрачное по (renderOrder, program, material, z), прозрачное —
  по (renderOrder, z по убыванию).

**Что брать:** битовые маски слоёв, `attach()` с сохранением мира, разделение
opaque/transparent, `renderOrder` как ручной override.
**Что не брать:** god-object в основании. `Object3D` знает про всё сразу, и в Dart
это ещё и означает жирный объект на каждый узел.

### Babylon.js — `Node` → `TransformNode` → `AbstractMesh` → `Mesh`

Иерархия разнесена по ответственностям: `Node` — имя и родство, `TransformNode` —
только трансформ, `AbstractMesh` — границы, материал, отбраковка, `Mesh` — геометрия.

- **Камеры и свет — тоже `Node`.** Значит камеру можно припарентить к движущемуся
  объекту бесплатно, без специального механизма «follow».
- `computeWorldMatrix(force)` с кэшированием, `setParent()` сохраняет мир.
- `renderingGroupId` (0..3) — грубый порядок групп, `alphaIndex` — внутри.
- `scene.activeCamera` и `activeCameras`; у каждой камеры свой нормализованный
  `viewport` и `layerMask` — так делается split-screen и мини-карта.

**Что брать:** чистый трансформный узел без рендер-нагрузки (группировка и
пивоты становятся бесплатными) и **камера как узел сцены**.

### PlayCanvas — ECS + слои как контракт

`GraphNode` — трансформ и иерархия; `Entity` = `GraphNode` + компоненты
(render, camera, light, script, collision). Композиция вместо наследования.

Самое интересное — слои:

- Слой это буквально «список мешей для отрисовки», и он **автоматически делится
  на Opaque и Transparent** подслои по материалу.
- У камеры есть **приоритет** и **список слоёв**, которые она рисует. UI-камера
  рисует только UI-слой.
- У каждого подслоя свой **режим сортировки**: Material/Mesh (минимум смен
  состояния — дефолт для opaque), Back-to-Front (дефолт для transparent),
  Front-to-Back, Manual (по `drawOrder`), None. Плюс `drawBucket` (0–255) как
  грубый первичный ключ.
- Итоговый порядок: приоритет камеры → порядок слоёв → режим сортировки подслоя.

**Что брать:** композицию вместо наследования; слои как явный контракт между
сценой и кадром; **режимы сортировки как настройка, а не как политика, вшитая в
рендерер**.

### Сводка

| | three.js | Babylon.js | PlayCanvas |
|---|---|---|---|
| Основание | `Object3D` (всё в одном) | `Node`→`TransformNode`→`Mesh` | `GraphNode` + компоненты |
| Камера в графе | да (наследник) | да (наследник `Node`) | компонент на Entity |
| Обновление матриц | грязный флаг + обход раз в кадр | кэш + `computeWorldMatrix` | грязные флаги на `GraphNode` |
| Фильтр видимости | битовая маска `layers` | `layerMask` | слои-списки + маска |
| Порядок отрисовки | `renderOrder` + сортировка в рендерере | `renderingGroupId` + `alphaIndex` | приоритет камеры → слои → sort mode |
| Multi-view | несколько `render()` + scissor | `activeCameras` + `viewport` | камеры с приоритетом |

## 3. Что добавляют наши ограничения

Это не косметика — три ограничения меняют выводы по сравнению с web-движками.

**1. Шейдеры компилируются AOT, пайплайн — дорогое и грубое состояние.**
В web-движках смена шейдера дешёвая, поэтому сортировку по материалу можно
считать оптимизацией. У нас пайплайн создаётся заранее и переключение внутри
прохода стоит дороже, а перестановок мало и они крупные (модель освещения ×
режим блендинга). Значит **пайплайн обязан быть старшим ключом сортировки**, а не
приятным дополнением. Режим PlayCanvas «Material/Mesh» для нас — основной.

**2. Dart GC.** Аллокации в кадре недопустимы. Отсюда:
- обход дерева каждый кадр для сбора отрисовки — плохая идея, нужен **плоский
  реестр рендерящихся объектов**, который сцена поддерживает при attach/detach;
- render list — переиспользуемый буфер изменяемых записей, а не свежий список
  объектов;
- ключи сортировки — упакованные в `int` (в Dart он 64-битный), сортируем
  массив индексов, а не список объектов с компаратором-замыканием;
- трансформы читаются в переданный `out`-вектор, а не возвращают новый.

**3. Compute нет, отбраковка только на CPU.** Значит мировые границы объектов
должны быть закэшированы и инвалидироваться дешево.

## 4. Принятое решение

**Выбрана модель three.js: классическое дерево с наследованием** —
`MeshNode` / `CameraNode` / `LightNode` наследуют `SceneNode`.

Важная оговорка к этому выбору: наследование **не обязывает** обходить дерево
каждый кадр. Babylon держит классическую иерархию и при этом плоские массивы
`scene.meshes` / `lights` / `cameras` рядом с ней. Сделано так же:
`Scene` поддерживает реестры при attach/detach, поэтому отбраковка — линейный
проход по непрерывному списку, а `traverse` остаётся для пользовательского кода.
Так сохраняется и привычный API, и свойство, важное именно в Dart.

`SceneNode` при этом держится узким (только трансформ, иерархия, видимость,
маска слоёв), то есть разделение ответственностей из Babylon выражено через
наследование, а не через компоненты.

### 4.1 Альтернатива, которая рассматривалась: узел + компоненты

Ни чистое дерево three.js, ни полный ECS — середина:

- `SceneNode` — **только** имя, родство, трансформ, видимость, маска слоёв.
  Никакой геометрии, никакого материала. Это `TransformNode` из Babylon.
- Рендерящаяся геометрия, камера и свет — **вложения** (компоненты) на узле,
  а не его подклассы. Узел может нести и меш, и свет одновременно.
- Никакой ECS-машинерии: ни архетипов, ни систем. Компоненты — типизированные
  слоты.
- **Сцена держит плоские реестры**: `renderables`, `lights`, `cameras`,
  обновляемые при attach/detach. Рендерер итерирует их линейно и никогда не
  обходит дерево.

Последний пункт даёт главную выгоду ECS (линейный проход по непрерывному списку)
без его стоимости, и прямо отвечает на проблему GC.

```dart
final class SceneNode {
  String? name;
  SceneNode? get parent;
  Iterable<SceneNode> get children;

  // TRS меняется только через методы: в Dart нельзя перехватить мутацию
  // возвращённого Vector3, а ручной markDirty() — источник тихих ошибок.
  void setPosition(double x, double y, double z);
  void setRotation(Quaternion q);
  void setScale(double x, double y, double z);
  void translate(double x, double y, double z);

  // Чтение без аллокации.
  Vector3 readPosition([Vector3? out]);

  Matrix4 get worldMatrix;   // валиден всегда, см. 4.2
  int get worldVersion;

  bool visible;
  int layerMask;             // битовая маска, как three.js layers

  void add(SceneNode child);
  void remove(SceneNode child);
  void attach(SceneNode child);  // перепривязка с сохранением мира
}
```

### 4.2 Версии вместо грязных флагов

three.js и Babylon требуют отдельного прохода обновления (`updateMatrixWorld`)
или явного `computeWorldMatrix`. Забыть его — классическая ошибка, дающая кадр
задержки.

Предлагается **счётчик версий**: у узла есть `_localVersion` и запомненная
`_seenParentVersion`. Геттер `worldMatrix` при обращении сравнивает версию
родителя со запомненной и пересчитывает при расхождении, рекурсивно поднимаясь
вверх.

Свойства:
- отдельный проход обновления **не нужен вообще** — устаревший трансформ
  структурно невозможен;
- изменение узла не требует обхода поддерева (в отличие от push-down флага);
- стоимость запроса — O(глубины) в худшем случае, а обычно O(1) по кэшу;
- `worldVersion` бесплатно даёт инвалидацию всего производного: мировых границ,
  матрицы вида камеры, обратной матрицы для нормалей.

### 4.3 Камера: проекция отдельно от размещения

```dart
sealed class Projection {
  Matrix4 toMatrix(double aspect);
}
final class PerspectiveProjection implements Projection { double fovY, near, far; }
final class OrthographicProjection implements Projection { double height, near, far; }

final class CameraComponent {
  Projection projection;
  // Матрица вида берётся из узла: worldMatrix.inverted(), кэш по worldVersion.
}
```

Камера — компонент на узле, значит парентится как всё остальное: камера в кокпите
самолёта это просто дочерний узел. Контроллеры (orbit, fly, first-person)
управляют **узлом**, а не камерой, поэтому тот же orbit-контроллер годится, чтобы
крутить источник света вокруг модели.

`perspectiveZeroToOne` из `projection.dart` становится реализацией
`PerspectiveProjection.toMatrix` — соглашение о глубине `[0, 1]` остаётся в одном
месте, и юнит-тесты продолжают его пришпиливать.

### 4.4 RenderView — то, что делает multi-view бесплатным

Сущность, которую принимает рендерер вместо «камеры и размеров»:

```dart
final class RenderView {
  CameraComponent camera;
  Rect viewportFraction;   // нормализованный, как в Babylon
  int layerMask;           // что эта камера видит
  int priority;            // порядок между камерами, как в PlayCanvas
  ClearSettings clear;
  RenderTargetSpec target; // размер, MSAA, форматы
}
```

Отсюда бесплатно получаются: split-screen, мини-карта, рендер в текстуру для
отражений, а позже — проходы теней (камера света — это тоже `RenderView`).

### 4.5 Render list и упакованные ключи сортировки

```dart
// Пулится и переиспользуется между кадрами.
final class DrawItem {
  GpuMesh mesh;
  Material material;
  Matrix4 worldMatrix;
  double viewDepth;
  bool flipWinding;
}
```

Ключ сортировки пакуется в один `int` и сортируется как массив индексов:

```
opaque:      [ drawBucket:8 | pipelineId:12 | materialId:20 | depth:24 ]  → по возрастанию
transparent: [ drawBucket:8 |        invDepth:24 | pipelineId:12       ]  → дальние первыми
```

Пайплайн старшим полем — прямое следствие AOT-шейдеров (§3.1). Глубина
квантуется в 24 бита, чего с запасом хватает для порядка отрисовки.

Режимы сортировки заимствуются у PlayCanvas как **настройка**, не как политика:
`stateThenDepth`, `backToFront`, `frontToBack`, `manual`, `none`.

### 4.6 Слои

Начать с малого: битовая маска на узле (three.js) + маска на `RenderView`, а
разделение opaque/transparent выводить из `AlphaMode` материала — то есть
подслои PlayCanvas без объекта `LayerComposition`. Полноценный упорядоченный
список слоёв понадобится вместе с пост-обработкой, тогда и добавится.

### 4.7 Ассет против экземпляра

Разделение, которого сейчас нет и которого не хватает:

- `ModelAsset` — загруженные на GPU меши, материалы, текстуры. Иммутабелен,
  переиспользуем, кэшируется.
- `asset.instantiate(scene, parent)` — строит узлы и вложения. Одна модель может
  стоять в сцене сколько угодно раз, разделяя `GpuMesh` и текстуры.

glTF-декодер уже переиспользует `MeshData` между узлами; это восстанавливает
преимущество на уровне GPU и заодно сохраняет иерархию glTF, которую `GpuModel`
сейчас теряет.

### 4.8 Поток кадра

```
для каждого RenderView по возрастанию priority:
  1. aspect из viewport → projection.toMatrix
  2. view = camera.node.worldMatrix.inverted()   (кэш по worldVersion)
  3. извлечь frustum
  4. линейный проход по scene.renderables:
       visible? layerMask совпал? мировая сфера в frustum? → append DrawItem
  5. посчитать ключи, отсортировать индексы
  6. пройти отсортированное: bindPipeline только при смене, uniform'ы на draw
  7. present
```

Ни одного обхода дерева, ни одной аллокации в шагах 4–6.

## 5. Что придётся переписать

| Сейчас | Становится |
|---|---|
| `GpuModel` / `GpuDraw` | `ModelAsset` + `instantiate()`; `GpuDraw` → `MeshRenderable` (компонент) |
| Камера и `spinMatrix` в `render()` | `CameraComponent` на узле + контроллер; вращение — анимация узла сцены |
| `perspectiveZeroToOne` | `PerspectiveProjection.toMatrix` (та же математика, те же тесты) |
| Свет как константа в `render()` | `LightComponent` в реестре сцены |
| `render(width, height, model, …)` | `render(scene, view)` |
| Подгонка камеры по границам модели | `OrbitController.frameAll(scene)` |

Слой геометрии и glTF-декодер не затрагиваются — они уже ниже сцены и от неё не
зависят. Это, собственно, и было целью их изоляции.

## 6. Порядок работ

1. `SceneNode` с версиями трансформа + `attach`/`add`/`remove`. Тесты без GPU:
   композиция трансформов, сохранение мира при перепривязке, инвалидация по
   версиям, отсутствие устаревших матриц.
2. `Scene` с плоскими реестрами компонентов.
3. `CameraComponent` + `Projection`; перенос матрицы проекции и её тестов.
4. `OrbitController` + мост жестов Flutter (P1 из плана, слой 4).
5. `RenderView` и переход `Renderer.render(scene, view)` — рендерер начинает
   принимать сцену, но пока с одним видом.
6. Отбраковка по frustum + мировые границы с кэшем по `worldVersion`.
7. Render list с упакованными ключами и режимами сортировки.
8. `LightComponent`, несколько источников.
9. `ModelAsset.instantiate` и восстановление иерархии glTF.

Шаги 1–3 самодостаточны и сразу убирают захардкоженную камеру. Шаг 4 даёт
интерактивность, после которой демо становится осмысленным.

## 7. Открытые вопросы

- **Слои сейчас или потом.** Битовая маска стоит почти ничего, упорядоченный
  список слоёв — заметно дороже. Предлагается маска сейчас, список — вместе с
  пост-обработкой.
- **Анимация трансформов.** Появится в слое 8; версии узла уже дают ей
  правильную точку подключения, но состав API (треки → узлы) здесь не решается.
- **Многопоточность.** Отбраковка и сортировка в изоляте — заманчиво, но
  `SceneNode` тогда не должен быть графом ссылок. Пока не закладываемся, но
  плоские реестры этот путь не закрывают.

## 8. Что реализовано

Слои 1–7 из §6, кроме отбраковки-по-BVH и полноценных слоёв:

- `SceneNode` со счётчиками версий вместо грязных флагов, `add`/`attach`/`remove`,
  защита от циклов, `lookAt` и `setLocalForward`;
- `Scene` с плоскими реестрами `meshes`/`lights`/`cameras`;
- `MeshNode` с мировыми границами и признаком зеркальности, кэшируемыми по
  `worldVersion`;
- `CameraNode` + `Projection` (`PerspectiveProjection`, `OrthographicProjection`),
  матрица вида кэшируется по `worldVersion`;
- `LightNode` (directional / point / spot), направление из локального -Z;
- `OrbitController` + мост жестов Flutter (drag / scroll / pinch / pan);
- `RenderView` с нормализованным вьюпортом, маской слоёв, приоритетом и режимами
  сортировки; рендерер принимает список видов;
- `RenderList` с отбраковкой по frustum, разделением opaque/transparent и
  упакованными в 64-битный int ключами сортировки;
- `ModelAsset` + `instantiate()` — разделение ассета и экземпляра;
- тонмаппинг (Khronos PBR Neutral) и экспозиция — всплыли как следствие того, что
  камерой стало можно управлять: блик GGX на скользящем угле давал 8375 пикселей
  чистого белого, после тонмаппинга их ноль.

Не сделано: упорядоченные слои (пока только битовая маска), несколько источников
света в шейдере, BVH, сохранение иерархии glTF при инстанцировании.

## 9. Меньше статики, больше абстракций

Отдельный проход по просьбе: статические методы заменены на полиморфные типы.

| Было | Стало | Что это даёт |
|---|---|---|
| `Primitives` с 8 статическими методами + свободная `revolve()` | `Shape` c реализациями `CuboidShape`, `SphereShape`, `LatheShape`, … | Фигура стала **значением**: её можно хранить, передавать, переопределить своей реализацией. `ProceduralSource` теперь держит `Shape`, а не замыкание |
| `perspectiveZeroToOne()` / `orthographicZeroToOne()` | математика внутри `PerspectiveProjection.toMatrix` / `OrthographicProjection.toMatrix` | Соглашение о глубине живёт в одном полиморфном месте, второй копии для расхождения нет |
| `projectToNdc()` свободная функция | метод на `Projection` | Проверять поведение можно через саму абстракцию |
| `GltfAccessorReader._readComponent` / `_readIntComponent` | `GltfComponentType.readDouble` / `readInt` | Правила (размер, асимметричная нормализация знаковых) — свойства самого типа компонента |
| `GltfLoader._toTriangleList(mode, …)` | `GltfPrimitiveMode.toTriangleList()` + `isTriangles` | Switch стал исчерпывающим по построению |
| `checkerboardRgba8()` / `whiteRgba8()` + статик в виджете | `ProceduralTexture` с `CheckerboardTexture`, `SolidColorTexture` | Путь загрузки написан один раз, генерация пикселей тестируема отдельно |
| `Material.sortId` со статическим счётчиком | `MaterialSortIds`, которым владеет `RenderList` | Убрана глобальная изменяемая статика — худший вид статики для тестов |

Осталось намеренно: приватный `SceneNode._versionCounter` (счётчик версий обязан
быть глобальным, иначе перепривязка между узлами с совпавшими номерами
проходит незамеченной — это проверено тестом) и фабричные конструкторы
(`ModelAsset.fromMesh`, `Renderer.create`), которые в Dart идиоматичны.

Попутно `BoxShape` переименован в `CuboidShape`: `flutter/material.dart`
экспортирует свой `BoxShape`, и совпадение имён заставляло бы каждое приложение
разруливать конфликт импортов.
